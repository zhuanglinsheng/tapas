# Tapas 可验证 Agent 环境设计

本文讨论 Tapas 的一个潜在发展方向：用于声明可验证的 AI Agent 业务环境，并
自动生成一致的初始状态、工具接口、交互任务、结果判定和可回放轨迹。

本文是一份方向设计，而非当前语言规范。文中的说明性语法均使用 `text` 代码块，
不表示现有编译器已经支持这些写法。只有经过真实用户和原型验证的部分，才应进入
语言规范和实现计划。



## 1. 问题

工具型 AI Agent 不再只生成文本，而是通过 API 修改真实系统中的状态，例如：

- 查询和取消订单；
- 改签航班；
- 处理退款和争议；
- 转账或冻结账户；
- 更新 CRM；
- 调整订阅；
- 创建采购单；
- 处理保险理赔。

未经充分验证的 Agent 不能直接操作生产系统。开发者需要一个模拟环境，使 Agent
能够调用与生产系统相似的工具，并根据最终状态判断任务是否完成。

现在，这类环境通常由 Python 手工实现。一个完整环境至少包含：

1. 数据库 Schema 和初始数据；
2. Agent 可以调用的工具；
3. 工具的前置条件和状态转换；
4. 权限与业务政策；
5. 模拟用户及其目标；
6. 测试任务；
7. 成功与失败的判定条件；
8. 环境重置、日志和回放。

这些部分由不同代码分别维护时，很容易互相矛盾。例如，初始数据可能包含业务上
不可能出现的状态；工具可能允许本应禁止的操作；结果判定器也可能只检查一个
表面字段，而没有检查系统是否仍满足关键不变量。

本方向试图解决的核心问题是：

> 如何通过一份声明建立业务世界的单一事实来源，并保证生成的状态、操作、任务和
> 判定始终遵循同一套规则？



## 2. 产品目标

Tapas 环境定义应能够生成或驱动以下制品：

- 合法且可复现的数据库初始状态；
- Agent 工具的参数 Schema 与实现入口；
- 工具调用后的状态转换；
- 全局业务不变量；
- 用户目标和测试任务；
- 任务成功条件；
- 边界情况和罕见情景；
- 完整事件轨迹；
- 失败原因和最小失败案例。

可以用一句话概括这一方向：

> 声明一次业务世界，自动得到可交互、可验证、可回放的 Agent 测试环境。

它与 Stan 的产品结构具有类比关系：Stan 用户声明概率模型，系统负责推断；Tapas
用户声明业务环境与不变量，系统负责构造环境、执行交互并验证结果。约束传播、
搜索和模拟都是内部机制，不是面向用户的产品定位。

约束传播可能成为这个方向的关键技术优势，但前提是它改变用户能完成的工作，而不
只是把“数据不合法”检查得更快。最有价值的结果是：用户给出罕见状态的部分条件，
系统直接构造完整合法环境；当条件冲突或 Agent 失败时，系统还能解释原因并生成
更小的反例。单独提供约束求解 API 不构成这一产品。



## 3. 非目标

这个方向不意味着 Tapas 要成为：

- 通用约束求解器；
- 新的数据库；
- 完整业务流程管理系统；
- 企业生产系统的替代品；
- 只生成统计相似表格的合成数据工具；
- 只面向某一个 Agent 框架的 Benchmark；
- 能够形式化证明任意程序正确的验证系统。

第一阶段也不追求自动学习全部业务规则。环境作者仍需明确声明实体、操作、政策和
不变量。系统负责组合、检查和执行这些声明。



## 4. 用户与工作流

### 4.1 环境作者

环境作者理解目标业务系统，负责声明：

- 有哪些实体；
- 哪些状态组合合法；
- Agent 能调用哪些工具；
- 每个工具何时允许调用；
- 调用会如何修改状态；
- 哪些政策限制 Agent 行为；
- 怎样判断任务成功。

环境作者可能是 Agent 工程师、测试工程师、领域工程师或负责评估的研究人员。

### 4.2 Agent 开发者

Agent 开发者通过标准工具接口连接环境，批量运行任务，查看成功率、失败轨迹和
边界案例。他们不必理解环境使用了何种约束算法。

### 4.3 评审者

评审者检查任务是否合理、环境是否遗漏关键政策、判定条件是否过弱，以及某次
失败究竟来自 Agent、工具实现还是环境本身。

### 4.4 典型流程

```text
声明业务环境
    -> 检查 Schema、状态机和不变量
    -> 生成或导入初始世界
    -> 生成测试任务
    -> 启动隔离环境并暴露工具
    -> Agent 与模拟用户交互
    -> 记录每次工具调用和状态变化
    -> 检查最终状态和过程约束
    -> 生成结果、解释和回放
```



## 5. 核心语义

一份环境由实体、关系、状态、操作、不变量、政策、场景和判定组成。

### 5.1 实体

实体是业务世界中具有稳定身份和可变状态的对象。例如，银行环境可能包含客户、
账户和转账：

```text
entity Customer {
    id: CustomerId
    kyc: Unverified | Pending | Verified
    risk: Low | Medium | High
}

entity Account {
    id: AccountId
    owner: CustomerId
    balance: Money
    status: Active | Frozen | Closed
}

entity Transfer {
    id: TransferId
    source: AccountId
    destination: AccountId
    amount: Money
    status: Pending | Settled | Reversed
    created_at: Time
}
```

实体声明应同时为编译器、运行时、数据库适配器和 Agent 工具提供结构信息，而不是
在四个位置重复编写 Schema。

### 5.2 关系

实体之间可以存在一对一、一对多和多对多关系。关系声明不仅描述外键，还可以
包含基数和条件约束：

```text
relation Account.owner -> Customer.id {
    each Account has exactly 1 Customer
    each Customer has 0..* Accounts
}

relation Transfer.source -> Account.id
relation Transfer.destination -> Account.id

constraint Transfer.source != Transfer.destination
```

删除或修改实体时，关系规则决定操作是否被禁止、级联或转化为历史记录。

### 5.3 状态机

许多业务实体具有明确生命周期。状态机应当成为一等声明，而不是分散在多个工具
函数中的条件判断：

```text
state Transfer.status {
    Pending -> Settled
    Pending -> Cancelled
    Settled -> Reversed

    terminal Cancelled
    terminal Reversed
}
```

任何工具都不能产生未声明的状态转换。系统还应检查不可达状态、没有出口的非终止
状态和相互冲突的转换条件。

### 5.4 不变量

不变量在环境建立后和每次操作完成后都必须成立：

```text
invariant Account.balance >= 0

invariant Account.status == Closed
    implies Account.balance == 0

invariant Transfer.status == Reversed
    implies Transfer.reversed_at != Nil
```

不变量可以作用于单个实体、实体关系或整个世界。全局不变量的代价可能很高，环境
作者应能够区分需要每次检查的关键不变量和仅在批量验证时检查的完整不变量。

### 5.5 操作

操作定义 Agent 可以调用的工具。它包含参数、前置条件、状态变化和后置条件：

```text
action reverse_transfer(transfer_id: TransferId) -> ReversalResult {
    let transfer = Transfer[transfer_id]
    let source = Account[transfer.source]
    let destination = Account[transfer.destination]

    requires transfer.status == Settled
    requires now - transfer.created_at <= 24 hours
    requires source.status != Closed
    requires destination.status == Active

    effect {
        transfer.status = Reversed
        transfer.reversed_at = now
        source.balance += transfer.amount
        destination.balance -= transfer.amount
    }

    ensures total_balance() == old(total_balance())
}
```

`requires` 描述调用是否允许；`effect` 描述原子状态转换；`ensures` 检查操作完成后
必须成立的关系。`old(expression)` 读取操作开始前的值。

操作需要事务语义。任何前置条件失败、运行时错误或后置条件失败，都必须回滚本次
操作产生的全部状态变化。

### 5.6 政策

操作描述系统能力，政策描述在特定上下文中谁可以使用这些能力：

```text
policy HighValueTransfer {
    when transfer.amount > 10000
    require customer.kyc == Verified
}

policy HighRiskReversal {
    when customer.risk == High
    forbid direct action reverse_transfer
    require action create_dispute
}
```

把政策与操作分开，可以在不复制工具实现的情况下切换地区、客户类型或产品规则，
也便于测试 Agent 是否遵守政策，而不是仅仅成功修改最终状态。

### 5.7 场景

场景描述一类测试环境，而不必写出每个实体的完整值：

```text
scenario MistakenTransfer {
    given {
        let customer: Customer
        let source: Account where owner == customer.id
        let destination: Account where owner != customer.id
        let transfer: Transfer {
            source == source.id
            destination == destination.id
            status == Settled
            age in 1 hour .. 20 hours
            amount in 10 .. 5000 CNY
        }
    }

    user_goal "Reverse the transfer sent to the wrong account."

    success {
        transfer.status == Reversed
        source.balance == old(source.balance) + transfer.amount
        destination.balance == old(destination.balance) - transfer.amount
    }
}
```

场景的 `given` 部分描述需要满足的关系，由生成器补全未指定值。`success` 描述任务
结束时必须成立的条件。场景还可以声明禁止出现的过程行为，例如不得绕过权限直接
修改数据库。



## 6. 约束规划与传播

约束传播不是产品名称，也不应暴露为要求用户学习的通用求解接口。它是连接环境
声明与实际产物的核心执行机制：同一组实体关系、状态转换、政策和不变量，既用于
构造合法世界，也用于生成边界任务、解释矛盾和缩减失败案例。

如果系统只在随机生成数据后执行布尔检查，那么约束只是校验器。这样的实现能够
拒绝错误样本，却无法有效找到罕见的合法状态，也不能从部分条件反推出其余世界。
本方向的关键差异在于：尽可能让业务规则参与构造过程，而不只在构造结束后验收。

### 6.1 两类约束

语言必须明确区分**可传播约束**和**仅可检查条件**。

可传播约束属于受限、可分析的声明片段，可以参与领域收缩和搜索。第一阶段包括：

- 相等、不等和有序比较；
- 有限枚举域与集合成员关系；
- 整数、Decimal、Money 和 Time 的有限区间；
- 实体引用、基数、存在性和唯一性；
- 布尔蕴含与有限析取；
- 状态机允许的转换；
- 简单线性算术；
- 少量经过验证的全局约束，例如 `all_different` 和计数限制。

普通 Tapas 函数和外部调用可以写出更复杂的条件，但任意代码通常无法安全地反向
推理。此类条件只能在一个完整候选世界上检查，不能承诺参与传播、边界推导或矛盾
核心提取。例如，调用外部风控模型得到的分数可以作为最终检查项；除非该模型提供
专门的可传播抽象，否则生成器不能从目标分数反推出客户和交易字段。

编译器应在静态分析时标明每条规则的能力：

```text
constraint kind:
    propagatable   # 可参与传播、搜索和解释
    check_only     # 仅在候选世界完整后执行
```

这不是实现细节。环境作者必须知道一条规则为何无法用于定向生成，也必须能够选择
补充可传播近似、接受较慢的候选检查，或者缩小场景范围。

### 6.2 领域与传播器

在生成阶段，尚未确定的字段不保存一个占位值，而保存一组可能值，即它的**领域**：

```text
transfer.status : {Pending, Settled, Reversed}
transfer.amount : [1, 5000] CNY
customer.kyc    : {Pending, Verified}
```

每条可传播约束降低一个或多个领域的可能范围。例如：

```text
transfer.status == Reversed
    implies customer.kyc == Verified

transfer.status = {Reversed}
    => customer.kyc: {Pending, Verified} -> {Verified}
```

传播器把发生变化的字段放入工作队列，反复执行相关约束，直到所有领域稳定或某个
领域变为空。空领域表示当前条件互相矛盾。若传播结束后仍有多个可能值，生成器才
进行有记录的分支、采样或调用后端搜索，然后继续传播。

```text
部分场景
    -> 建立字段领域
    -> 传播至不动点
    -> 矛盾：提取原因
    -> 未确定：选择分支或按分布采样
    -> 再次传播
    -> 执行仅可检查条件
    -> 得到完整合法世界
```

每次领域缩小都应保存原因，包括触发的约束、来源位置和前一步推导。该信息同时
服务于编译诊断、生成日志、矛盾解释和失败缩减，不能在各功能中分别重建。

### 6.3 罕见合法状态生成

这是约束传播最可能形成实际优势的能力。Agent 的严重错误通常出现在多个低概率
条件同时成立时，而不是常见的正常流程。例如，一个银行场景可能要求：

- 转账已经结算但仍处于允许撤销的时间窗口；
- 收款账户在结算后被冻结；
- 付款客户已经完成 KYC；
- 金额刚好触发人工复核政策；
- 退款后两个账户都不得出现负余额。

若分别随机生成客户、账户和转账，再等待这些条件偶然同时成立，拒绝采样可能几乎
永远得不到样本。传播从目标条件出发收缩时间、状态、余额和身份领域，只在剩余空间
中选择具体值，因此能够直接构造罕见但合法的世界。

生成结果必须能由随机种子和完整决策记录复现。系统还应记录哪些值由约束唯一确定，
哪些值来自搜索，哪些值来自概率采样，以便解释一个任务为何出现。

### 6.4 部分世界与双向推导

场景作者不应为了获得一致数据而填写所有字段。他们可以指定任意一部分事实，让
系统补全其余部分：

```text
given transfer.status == Reversed
given transfer.amount > 10000 CNY

inferred customer.kyc == Verified
inferred transfer.previous_status == Settled
inferred source.balance_before >= transfer.amount
```

推导不固定沿着程序执行方向进行。余额守恒既可从交易前余额推出交易后余额，也可
从目标余额反推出允许的交易金额；实体关系既可由订单找到客户，也可根据客户条件
筛选可引用的订单。这里的“双向”仅限于声明为可传播的关系，并不表示系统能够自动
反演任意 Tapas 函数。

部分世界还可以用于交互式环境设计：作者添加一个条件后，语言服务器立即展示被
收缩的字段域、必然成立的事实和新产生的矛盾。即使未来 AI 承担大部分代码编写，
这种可检查的语义反馈仍是环境质量控制的一部分。

### 6.5 边界案例

环境可以从比较、区间和政策阈值中系统化地产生边界任务：

- 允许撤销期限前一秒和后一秒；
- 金额刚好位于风控阈值两侧；
- 余额恰好足够或差一个最小货币单位；
- 权限刚刚过期；
- 状态转换与另一个事件同时发生；
- 两项政策单独适用和同时适用。

边界值不是在字段上独立扰动。改变时间或金额后，传播器必须同步调整依赖实体，
保证生成的正反案例仍是完整、合法且仅在目标边界上存在关键差异。相比盲目增加
随机样本，这类成对场景更容易暴露 Agent 对政策阈值和优先级的误解。

### 6.6 矛盾与来源解释

环境生成失败时，只报告“无解”没有实际价值。系统应给出尽可能小且面向领域的
冲突集合：

```text
Scenario `MistakenTransfer` cannot be constructed.

Required by the scenario:
  transfer.status == Reversed
  transfer.age == 30 hours

Required by policy `ReversalWindow`:
  a reversed transfer must be at most 24 hours old

Sources:
  scenarios/mistaken_transfer.tap:12
  policies/reversal.tap:31
```

解释来自传播过程中保存的原因图。后端返回的变量编号、子句或不可满足核心必须映射
回实体字段、政策、不变量和源代码位置。对于 `check_only` 条件，系统只能报告候选
世界未通过检查，不应伪装成完整的因果解释。

### 6.7 失败案例缩减

Agent 失败后，系统可以把“仍会触发同一失败”作为目标约束，尝试删除实体、关系、
事件和无关字段，并在每次删除后重新传播：

```text
Original world:
  40 customers, 120 accounts, 800 transfers

Reduced counterexample:
  1 customer, 2 accounts, 1 transfer, 1 freeze event
```

传播可以迅速排除破坏前置条件或业务一致性的删除方案，重放则确认 Agent 的失败仍然
存在。缩减结果应保留失败类型、关键轨迹和所有环境不变量。它的目标是产生便于理解
和回归测试的小案例，不承诺数学意义上的全局最小。

### 6.8 概率与约束的关系

约束回答“哪些世界合法”，概率回答“合法世界中哪些更常见”。二者不能互相替代。
生成器应先通过传播排除非法空间，再在剩余选择中应用声明的分布或经验数据：

```text
legal worlds = satisfy(schema, relations, policies, invariants)
sample        = probability_distribution conditioned on legal worlds
```

默认测试可以贴近真实业务分布，压力测试则可以提高罕见状态和边界组合的权重。若先
独立采样再拒绝非法结果，低概率交叉条件会导致严重浪费，也很难说明最终样本实际
服从什么分布。

### 6.9 后端边界与产品壁垒

实现可以组合有限域传播、区间传播、SAT、SMT、CP 或专用搜索后端，不必从头开发
通用求解器。Environment IR 负责保存领域语义、约束能力、来源和后端无关表示；
适配层只把其中可支持的片段降低到具体后端。

约束规划算法本身已有成熟实现，不足以形成 Tapas 的长期差异。真正需要积累的是：

- 能统一实体、状态、政策、操作和判定的 Environment IR；
- 适合业务系统的传播器与全局约束库；
- 从后端结果到领域规则和源代码的解释链；
- 可复现生成、执行、回放和缩减的一体化协议；
- 经过真实 Agent 任务验证的环境与反例语料。

因此，是否采用某种求解后端是可替换的工程决策；能否从一份业务声明稳定产生高价值
环境，并在失败时给出领域化解释，才是产品是否成立的判断标准。

### 6.10 决定性演示

约束传播是否构成核心优势，不能以“支持多少种约束”衡量。一个有说服力的演示应
完成整条闭环：

1. 环境作者只声明一个罕见银行撤销场景的目标条件；
2. 多项跨实体、金额、时间、状态和权限政策共同参与传播；
3. 系统构造出一个完整合法、可复现且不依赖海量拒绝采样的初始世界；
4. 加入一条故意冲突的政策后，系统指出最小冲突及其源代码来源；
5. Agent 在该世界中调用工具并产生错误；
6. 系统把失败缩减为少量实体和事件，并准确重放。

如果这些步骤需要环境作者分别编写生成器、校验器、判定器和缩减脚本，约束机制就
没有形成产品价值。如果它们由同一份领域声明和同一条原因链派生，才说明 Tapas
提供了手写 Python 环境难以低成本复现的能力。



## 7. 执行与验证

### 7.1 隔离世界

每项任务在独立世界中执行。任务之间不得共享可变状态、随机数状态或模拟时间。
环境重置应当通过加载不可变快照或重新执行可复现生成记录完成。

### 7.2 虚拟时间

Agent 环境不能依赖宿主真实时间。所有期限、超时、排程和事件均使用环境虚拟时间：

```text
clock starts at 2026-01-01T09:00:00Z
advance 2 hours
```

只有明确的操作或事件才能推进时间。这可以保证任务重放得到相同结果。

### 7.3 工具协议

环境应从 `action` 声明生成工具描述，包括：

- 名称和文档；
- 参数 JSON Schema；
- 返回值 JSON Schema；
- 可结构化返回的前置条件错误；
- 对应运行时入口。

协议适配器可以把同一操作暴露为本地调用、HTTP、MCP 或 Benchmark 自定义接口。
核心语义不能依赖其中某一种协议。

### 7.4 判定

任务判定至少包含三层：

1. 最终状态是否满足 `success`；
2. 整个过程中是否保持全局不变量；
3. Agent 是否遵守禁止绕过的政策和操作路径。

仅检查最终字段可能奖励通过非法操作达到正确结果的 Agent。环境必须同时保存状态
轨迹和操作轨迹。

### 7.5 回放

一次执行记录应包括：

- 环境及语言版本；
- 场景名称；
- 随机种子或生成记录；
- 初始状态哈希；
- 每次用户消息；
- 每次 Agent 输出；
- 工具调用及结果；
- 状态差异；
- 虚拟时间变化；
- 最终判定和解释。

同一版本环境加载记录后，应能够在不调用原 Agent 的情况下重放全部状态变化。



## 8. 与相关工具的边界

### 8.1 手写 Benchmark

手写 Benchmark 可以精确实现一个领域，但数据库、工具、任务和判定通常是独立的
Python 代码。Tapas 的目标是从同一份领域声明生成或验证这些组件，并让不同领域
共享相同的实体、操作、场景和回放语义。

### 8.2 合成数据工具

合成数据工具主要生成统计上接近真实数据的表格、关系或序列。可验证 Agent 环境
还必须描述：

- 数据如何通过操作变化；
- 哪些操作在当前状态允许；
- 权限和政策如何限制行为；
- 用户希望完成什么；
- 最终状态是否正确；
- 过程是否违反规则。

环境可以导入合成数据工具的样本，也可以把自身生成的数据导出给它们，但两者产物
不同。

### 8.3 Scenic

Scenic 面向自动驾驶、机器人等物理环境，擅长通过概率、几何和时空约束生成场景。
本方向面向企业系统中的实体、交易、权限、政策和工具调用。二者共享“声明世界而
不是手写每个测试”的思想，但领域语义和运行时接口不同。

### 8.4 形式化验证

Tapas 可以在有限范围内检查矛盾和不变量，但第一阶段不承诺穷尽所有状态或证明
任意 Agent 正确。它主要通过合法生成、运行时监视、系统化场景和失败缩减提高测试
质量。



## 9. 与现有 Tapas 的关系

现有 Tapas 不应直接把普通 Dictionary 当作实体，也不应把所有函数自动解释为
Agent 操作。建议在普通语言之上增加显式环境层：

```text
Tapas 普通代码
    - 辅助函数
    - 数据转换
    - 结果分析
    - 自定义生成策略

environment 声明
    - 实体
    - 状态机
    - 不变量
    - 操作
    - 政策
    - 场景
    - 判定
```

编译器把环境声明降低为专用 Environment IR。普通 Tapas 字节码可以实现纯辅助
计算，但任何参与生成或验证的函数都必须满足可分析性和确定性要求。

现有组件可以承担以下职责：

| 现有组件 | 潜在职责 |
|---|---|
| AST 与 Source Span | 环境语法、诊断和来源映射 |
| 结构 Type | 实体、操作参数和结果 Schema |
| 模块接口 | 跨文件领域定义与政策包 |
| 工作区分析 | 引用、重命名和跨模块一致性 |
| Time | 虚拟时间值的基础表示 |
| Dictionary、List、Pair | 运行时快照和工具返回值 |
| C 扩展 | 数据库、协议和外部模拟器适配器 |
| 字节码 VM | 隔离执行辅助逻辑和操作实现 |

仍需新增的核心能力包括：

- 保存领域、约束能力和来源的 Environment IR；
- 稳定实体身份；
- 事务状态存储；
- 状态机与不变量；
- 虚拟时间；
- 字段领域、传播器工作队列和决策记录；
- 传播原因图与后端适配层；
- 可复现的传播、搜索和条件采样；
- 工具 Schema 导出；
- 轨迹记录与重放；
- 矛盾解释与案例缩减。



## 10. 确定性、安全与资源限制

Agent 环境会执行外部 Agent 发起的调用，必须比普通脚本会话提供更严格的边界：

- 默认禁止文件、网络、进程和真实系统时间；
- 原生扩展按能力白名单注册；
- 限制指令数、内存、实体数、事件数和工具调用数；
- 每个操作具有事务边界；
- 错误不能终止宿主进程；
- 不允许未记录的随机源；
- 环境版本和原生包版本写入轨迹；
- 敏感生产数据不得进入生成记录和错误报告。

这些限制需要由运行时保证，不能只依赖环境作者遵守约定。



## 11. 最小原型

第一阶段只实现一个零售订单环境，并限制领域对象为：

- Customer；
- Product；
- Inventory；
- Order；
- Payment；
- Shipment；
- Refund。

只支持以下语言能力：

1. 实体和字段；
2. 唯一键与实体引用；
3. 有限枚举状态；
4. 整数、Money 和 Time 的有限区间；
5. 相等、比较、成员、蕴含和简单线性约束；
6. 状态机；
7. `requires`、`effect`、`ensures`；
8. 局部和少量全局不变量；
9. 场景中的部分赋值和双向推导；
10. 可传播约束与 `check_only` 条件的静态区分；
11. 任务成功条件；
12. 确定性工具执行；
13. JSON 工具 Schema；
14. 事件轨迹和重放；
15. 带来源的领域收缩和矛盾解释。

初始状态生成先实现有限域、区间和简单线性传播，加上确定性的深度优先搜索与决策
记录，不必开发通用求解器。每个传播器都必须返回领域变化及其原因。需要更复杂搜索
时，应先接入现有 SAT、SMT 或 CP 后端；只有业务语义无法通过适配层表达时，才增加
专用传播器或自研算法。

原型应完成至少三类任务：

- 正常取消尚未发货的订单；
- 处理已经发货但符合退款政策的订单；
- 拒绝违反权限或时间限制的请求，并给出正确替代路径。



## 12. 验证标准

这个方向只有同时满足以下条件，才值得发展为 Tapas 的核心用途：

1. 一份环境声明能够派生数据库初始化、工具 Schema 和结果判定；
2. 相比手写 Python，环境定义显著减少重复业务逻辑；
3. 编译器能够发现现有手写环境中的不可能状态或过弱判定；
4. 从少量目标条件出发，生成器能够稳定构造拒绝采样难以得到的罕见合法状态；
5. 改变政策阈值后，系统能够生成仍然满足其余规则的成对边界任务；
6. 编译器能明确区分可传播约束和仅可检查条件，不对任意代码承诺反向推导；
7. 矛盾解释能定位到具体政策、前置条件或不变量，并显示对应来源；
8. 失败轨迹能够准确回放，并能缩减为保留同类失败的小案例；
9. 零售、航空和银行三个领域能够共享大部分 Environment IR 和基础传播器；
10. Agent 团队愿意维护声明式环境，而不是继续手写 Python；
11. 接入现有 Agent 框架不要求修改环境核心语义；
12. 传播、搜索和隔离执行的成本足以支持批量并行任务。

其中任何一项长期无法成立，都可能说明环境差异过大、声明语言抽象不正确，或者
用户并不需要独立语言。



## 13. 主要风险

### 13.1 领域差异过大

零售、银行、保险和 CRM 可能只有表面相似。如果共享 IR 最终只能表达数据库表和
普通函数，语言就没有足够价值。

### 13.2 声明与实现重复

如果操作仍需完整手写一次，再额外写 `requires` 和 `ensures`，环境作者可能认为
负担增加。设计必须尽量从声明派生实现、判定和文档，或者明确哪些部分只能手写。

### 13.3 约束生成扩展性

跨实体、跨时间和包含任意函数的约束可能难以求解。语言必须限制可传播片段，并为
不可分析代码提供清楚边界，不能声称能够自动生成任意复杂世界。`check_only` 条件
过多时，系统仍会退化为拒绝采样；传播片段过窄时，用户又会被迫重复描述规则。
原型应记录每个样本的传播次数、分支数、回溯数和检查拒绝率，以数据决定扩展哪些
传播能力。

### 13.4 环境与生产系统偏差

模拟环境越抽象，越可能遗漏真实系统行为。环境需要支持从生产 Schema、API 描述
和匿名轨迹导入信息，并通过契约测试检查模拟工具与真实接口是否一致。

### 13.5 评价标准本身错误

错误的 `success` 可能比错误的 Agent 更危险。系统应支持判定器测试、人工审查和
多层不变量，不能把一个布尔结果包装成绝对真相。



## 14. 研究验证与论文设计

完整实现一门语言和运行时，并不自动构成研究贡献。论文需要提出可以被实验否定的
主张，说明现有方法为何不足，并通过公开实现、对照实验和消融实验提供证据。

本方向最值得验证的核心主张是：

> 约束传播能够从统一业务声明中系统化地构造、诊断和缩减有状态 Agent 环境，并
> 发现固定任务、手写生成器和普通随机生成难以覆盖的业务失败。

论文不应把“支持一门新 DSL”作为主要结果。语言是承载实体、政策、操作和场景语义
的手段；罕见合法状态、可靠评价和可解释反例才是需要证明的效果。

### 14.1 研究问题

#### RQ1：统一声明是否减少重复和不一致

对比 AppWorld 风格的手写 Python 环境与 Tapas 环境，测量：

- 总实现量和领域规则的重复次数；
- 一个政策变化需要修改的位置；
- 数据生成、工具行为和判定器之间的不一致数量；
- 增加一个场景或业务实体所需的改动；
- 环境中有多少 Schema、工具说明和判定逻辑能够自动派生。

不能只比较代码行数。更有意义的是政策演化实验：例如修改退款期限或撤销条件，检查
两种实现是否同步更新了初始状态生成、工具前置条件和结果判定。

#### RQ2：传播是否提高罕见合法状态和边界状态的生成能力

随着目标条件越来越罕见，比较不同方法的：

- 合法样本比例和首个合法样本耗时；
- 传播次数、分支数、回溯数和拒绝率；
- 跨政策组合覆盖率；
- 阈值两侧的成对边界覆盖率；
- 无法满足时能否给出正确且足够小的冲突集合。

如果传播只在简单样本上略微提高速度，却不能稳定构造拒绝采样难以得到的交叉状态，
就不足以支撑这个方向的核心主张。

#### RQ3：生成环境是否发现新的 Agent 失败

在同一领域和同一组 Agent 上分别运行：

1. 人工编写的标准任务；
2. 普通随机任务；
3. 单项政策边界任务；
4. Tapas 生成的罕见政策组合任务。

实验应报告新增失败类别，而不只报告更低的成功率。例如：Agent 得到正确最终字段但
违反过程政策、在时间边界使用错误操作、两项政策同时生效时选择错误，或者恢复一个
实体时破坏另一个实体的不变量。每个新增失败都应能够重放，并由人工确认其业务含义
和判定正确性。

#### RQ4：解释和缩减是否改善诊断

对每个矛盾或 Agent 失败，测量：

- 原始与缩减案例中的实体、字段、事件和轨迹长度；
- 缩减后是否仍稳定触发同类失败；
- 冲突解释是否覆盖人工标注的真正规则；
- 不可满足核心及来源解释的大小；
- 不同后端是否给出一致的领域层结论。

在条件允许时，可以加入小规模开发者实验，比较原始轨迹和缩减反例的定位时间；早期
原型则应先保证上述客观指标可重复。

### 14.2 对照方法

实验不能只和最弱的随机生成器比较。至少应包含：

- AppWorld 风格的手写任务生成器；
- 纯拒绝采样；
- Hypothesis 风格的属性生成与有状态测试；
- 直接使用 Alloy、Z3 或 OR-Tools 建模的求解版本；
- Tapas 的领域传播、搜索和条件采样。

直接求解版本尤其重要，否则审稿人可能认为 Tapas 只是给现有求解器增加语法。对照
应区分求解时间、领域建模成本、来源解释、工具派生、执行和缩减，而不是只比较谁先
找到一个解。

还应进行消融实验，分别关闭专用传播器、原因记录、边界生成和失败缩减，确认结果
来自哪项机制。

### 14.3 实验制品

最小研究原型不需要先完成整个 Tapas，但应形成一条可复现的完整路径：

```text
环境声明
    -> Environment IR
    -> 传播与搜索
    -> 初始世界和工具 Schema
    -> Agent 执行
    -> 判定与轨迹
    -> 矛盾解释或失败缩减
```

制品至少包括：

- 可公开运行的编译器和环境运行时；
- 零售、航空和银行三个领域；
- 每个领域的规则、场景、工具和参考判定；
- 固定随机种子、版本和运行配置；
- 对照实现、实验脚本和原始结果；
- 人工审查过的失败分类和环境局限说明。

三个领域必须共享大部分 Environment IR 和基础传播器。如果每个领域都依赖独立生成
算法，实验只能证明三个专用系统可用，不能证明统一语言抽象成立。

### 14.4 可能的论文方向

这个项目可以形成两类不同论文，但不能把同一贡献简单拆分。

**软件测试与 Agent 评价论文**关注约束驱动的状态生成、政策边界、失败发现、解释
和缩减。软件工程方向可以考虑 ICSE、FSE、ISSTA 或 ASE；若主要贡献是可复用环境、
任务集和评价方法，则可以考虑 NeurIPS 的评估与数据方向、ICLR 或 ACL。其核心证据
是跨领域实验和相对现有生成方法的新失败发现。

**语言与编译系统论文**关注 Environment IR、可传播片段的静态判定、事务与不变量
语义、来源保持的约束降低、多后端适配，以及传播实现的正确性和性能。只有这些语言
与编译问题本身具有新意时，才适合 PLDI 或 OOPSLA 等编程语言会议；把 Python API
改写成 Tapas 语法并不足够。

第一篇论文通常应优先验证测试方法和真实需求。只有 Environment IR 与约束语义经过
跨领域验证后，再总结稳定的语言设计，能够降低过早形式化错误抽象的风险。

### 14.5 论文成立的最低门槛

研究结果至少应证明以下三点：

1. 同一条业务政策确实同时参与状态生成、工具执行和结果判定；
2. 约束传播发现了固定任务和普通随机生成没有覆盖的有效 Agent 失败；
3. 从环境构造到失败缩减始终保留可追踪、可重放的领域原因。

如果系统最终只是 AppWorld、Hypothesis 和某个求解器的薄语法包装，或者仍要求用户
分别手写生成器、校验器和缩减器，就没有形成足够强的研究贡献。



## 15. 研究与产品路线

### 阶段一：复刻现有环境

选择公开的零售、航空和银行 Agent 任务，提取共同概念，尝试以统一声明重新表达。
这一阶段不修改正式语言，只验证 Environment IR，并为每条规则标注它应当可传播
还是只能检查。

### 阶段二：单领域原型

完成零售订单环境的领域传播、搜索、工具执行、判定和回放。重点验证部分世界补全、
罕见合法状态、成对边界任务、矛盾解释和失败缩减，并与手写 Python 版本比较代码量、
样本质量、错误类型、运行成本和维护成本。

### 阶段三：跨领域验证

加入航空或银行环境，检查实体、状态、操作、政策和场景是否真正可以复用。如果需要
为每个领域增加大量特殊语义或传播器，应重新评估抽象边界。此阶段还应验证同一份
Environment IR 能否切换内部搜索后端，而不改变环境的公开语义。

### 阶段四：语言集成

只有前三阶段通过后，才把稳定概念加入 Tapas 语法、类型系统、编译器和语言服务器。

### 阶段五：生态接口

提供 Python SDK、HTTP/MCP 适配器、批量运行器和标准轨迹格式，使 Agent 团队能够
在不改变现有训练与评估框架的情况下采用 Tapas 环境。



## 16. 结论

这个方向的关键不是让 Tapas 同时成为约束求解器、模拟器和通用语言，而是建立一种
新的核心制品：**可验证的 Agent 业务环境**。

环境定义必须成为实体 Schema、工具行为、业务政策、测试任务和结果判定的共同来源。
约束传播使这些声明参与世界构造，而不只在最后执行校验，并用于生成罕见合法状态、
覆盖边界情况、解释矛盾和缩减失败案例；Tapas 的普通语言能力用于表达领域计算和
扩展接口；运行时负责隔离、事务、资源限制和确定性回放。

这一假设仍需通过复刻真实 Agent 环境验证。若统一声明不能显著减少手写 Python 的
重复逻辑，或者不同领域无法共享同一语义核心，就不应把它发展为语言方向。若验证
成功，Tapas 可以形成类似 Stan 的清晰定位：用户声明特定领域模型，系统自动完成
一组困难但边界明确的后续工作。



## 17. 参考项目与论文

- [τ-bench](https://taubench.com/) 及其
  [ICLR 2025 论文](https://proceedings.iclr.cc/paper_files/paper/2025/hash/1b126cc38b8638e07bef37e7b2bb72bf-Abstract-Conference.html)：
  通过模拟用户、工具和数据库状态评估真实业务任务中的 Agent；
- [AppWorld](https://appworld.dev/) 及其
  [ACL 2024 论文](https://aclanthology.org/2024.acl-long.850/)：提供可控应用、API、
  数据库、任务生成和状态判定，是本方向最重要的直接对照；
- [AutomationBench](https://github.com/zapier/AutomationBench)：在大量模拟 SaaS
  工具中评估业务流程自动化 Agent；
- [Scenic](https://docs.scenic-lang.org/en/latest/) 及其
  [PLDI 2019 论文](https://people.eecs.berkeley.edu/~sseshia/pubdir/pldi19-scenic.pdf)：
  通过概率和时空约束声明物理场景，并连接自动驾驶、机器人等模拟器；
- [Alloy](https://alloytools.org/spec.html)：在有限范围内寻找满足关系约束的实例、
  状态轨迹和反例，并支持不可满足核心；
- [Hypothesis Stateful Testing](https://hypothesis.readthedocs.io/en/latest/stateful.html)：
  生成有状态测试并缩减失败案例；
- [VerifAI](https://verifai.readthedocs.io/)：使用形式化规格引导模拟、反例搜索、
  参数合成和系统化测试；
- [Synthetic Data Vault](https://docs.sdv.dev/sdv)：生成单表、多表和时序合成
  数据，并支持业务约束；
- [Stan](https://mc-stan.org/)：通过专用概率模型语言连接领域声明、推断引擎、
  诊断和多语言生态，是本方向产品结构的重要参照。
