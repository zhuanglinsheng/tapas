## 1. 目标与设计边界

Tapas 应让用户定义空间与关系，由测试系统组织输入构造、实际执行、规则检查、记录及反例搜索，而不是要求用户用普通函数和循环手写测试运行器。

本设计首先面向离散、逐步交互的状态系统。一次操作有可识别的执行边界，执行前后可以获得状态或观察。并发交错、连续时间、概率分布和无界活性验证不属于第一版承诺。

核心方向：

1. 状态空间由枚举等 Type 的组合与 Rule 约束定义；其首要功能是成员判定和范围信息提供。
2. 第 k 类 Action 的参数空间由参数 Type、候选范围和 Rule 约束定义；不要求用户显式声明总 Action Space。
3. ActionInstance 表示参数已经固定的一次操作描述，不是一次执行，也不是一个规则判断。
4. 状态转移契约由引用前状态、操作参数、输出和后状态的 Rule 组合定义；逻辑蕴含已有第一版实现。
5. Rule 负责约束。新的测试构造负责角色绑定、执行时机、覆盖策略和运行记录，不另建一套独立约束语言。

不新增 `system` 来仅仅命名状态空间。空间是取值集合；系统还包含初始条件与动态行为。

## 2. 数学对象与术语

| 符号 | 对象 | 含义 |
|---|---|---|
| S₀ | 基础状态空间 | 状态 Type 可以表示的组合，包括可能违反状态规则的组合 |
| V(s) | 状态合法性谓词 | 状态组合必须满足的约束 |
| S | 合法状态空间 | S = {s ∈ S₀ ∣ V(s)} |
| I | 初始状态集合 | I ⊆ S，测试允许的起点，不一定包含所有合法状态 |
| k | Action 类别标识 | 区分不同种类的操作 |
| Pₖ⁰ | 基础参数空间 | 第 k 类操作的参数 Type 所允许的值 |
| Wₖ(p) | 参数构造约束 | 与具体执行状态无关的参数合法性规则 |
| Pₖ | 参数空间 | Pₖ = {p ∈ Pₖ⁰ ∣ Wₖ(p)} |
| a = k(p) | ActionInstance | 第 k 类操作与具体参数的绑定 |
| Oₖ | 输出空间 | 第 k 类操作可返回的业务输出 |
| Dₖ(s,p) | 契约适用范围 | 本契约承诺检查哪些状态与参数组合 |
| Cₖ(s,p,o,s′) | 转移契约 | 对一次执行前后关系的要求 |

“参数”有两个含义，必须区分：Rule 的形参可以包含状态、输出等任何待绑定变量；Action 的操作参数 p 仅指本次调用携带的输入。

整个调用集合在数学上可以写为带标签并集：

$
\mathcal A=\bigsqcup_{k\in K}\bigl(\{k\}\times P_k\bigr)
$

这是解释模型所需的数学对象，不要求在语言中增加总 Action Space 声明。

## 3. 状态空间：带类型参数的 Rule 定义集合

### 3.1 基础范围与组合约束

第一版可以从有限枚举的笛卡尔积开始：

$
S_0=E_1\times\cdots\times E_n,
\qquad
S=\{s\in S_0\mid V(s)\}
$

例如门禁的锁状态和门状态：

```text
let LockState = types::enum('锁定', '解锁')
let DoorState = types::enum('关闭', '打开')
let State = types::make_type(
    'lock': LockState,
    'door': DoorState,
)

let StateSpace = rule (state: State) {
    '门打开时必须处于解锁状态':
        (state['door'] == '打开') implies {
            state['lock'] == '解锁'
        }
}
```

`types::enum`、结构 Type、带参数 Rule 和上面的 `implies` 项已有基础实现。
State Type 提供四种基础组合，StateSpace 排除“锁定且打开”，得到三种合法状态。

StateSpace 仍是一个 Rule，不要求增加独立的 `space` 关键字。测试层将其标注为“状态集合定义”并消费其签名与 RuleIR。

### 3.2 成员判定与范围分析是不同能力

成员判定的数学含义是检查 V(s)。实际接口还需要区分 Type 不匹配、条件为假和求值错误，而不是把所有情况都归为“不在空间内”。

范围信息可以包括：

- 参数的结构、枚举成员和基础候选范围；
- 基础组合数上界，以及是否有限；
- 分析后收紧的候选范围；
- 已证实的精确成员数，或明确标记的上下界、估计值、未知值。

例如：

$
|S|\leq\prod_i|E_i|
$

这是确定的上界，不是筛选后数量的估计。有限域可以穷举后检查以得到精确集合，但代价可能随字段数指数增长。

Rule 可执行不等于 Rule 可静态分析。遇到普通函数调用、不可分析的扩展等，分析器必须报告不支持或保守范围，不得将不支持解释为空集。若报告包围合法集合的范围 B，必须保证 S ⊆ B；启发式采样得到的候选集合不能冒充这种上界。

### 3.3 合法空间与观察空间分开

即使 V(s′) 为假，测试系统仍应能保存 s′ 并报告状态违规。因此后状态的承载 Type 应是基础 State，而不是一个会在记录前拒绝所有非法组合的类型。

若实现返回连基础 Type 都不匹配的数据，则保存原始观察并报告类型或适配错误，不继续假装已经获得合法状态。

合法状态不等于可达状态。I 是初始集合；从 I 经实际执行或模型转移能够到达的状态才是可达集合。不得把“属于 S”自动解释为“可从 I 到达”。

初始状态可另用 Rule 定义：

```text
let InitialState = rule (state: State) {
    require StateSpace(state)
    state['lock'] == '锁定'
    state['door'] == '关闭'
}
```

## 4. 第 k 类 Action 的参数空间

### 4.1 参数类与 ActionInstance

参数空间同样由基础 Type 与 Rule 构成：

$
P_k=\{p\in P_k^0\mid W_k(p)\}
$

例如解锁操作接受一个凭据类别：

```text
let Credential = types::enum('有效凭据', '无效凭据')
let UnlockParameters = types::make_type('credential': Credential)

let UnlockParameterSpace = rule (parameters: UnlockParameters) {
    // 此例中两种凭据都可构造，不额外排除。
}
```

无效凭据是合法的测试输入，不能因为它应被业务拒绝，就从构造范围中排除。

Action 参数类至少关联：稳定的类别标识 k、参数 Type、参数空间 Rule，以及可选的候选范围来源。
从中构造 a = k(p)，得到 ActionInstance。ActionInstance 不包含执行结果，也不必绑定当前状态。

```text
// 概念记法，不是已确定的构造语法：
Unlock(credential: '有效凭据')
Unlock(credential: '无效凭据')
Open()
```

无参数操作的参数空间在数学上是单元素集合 {()}，不是空集。

RuleInstance 与 ActionInstance 不可混同：前者是 Rule 和实参的绑定，表示待判断的命题；后者是操作类别与实参的绑定，表示待执行的操作。检查参数 Rule 可以作为 ActionInstance 构造的一部分，但不会将 RuleInstance 自动变成 ActionInstance。

### 4.2 参数范围与当前状态下的允许范围

状态相关的允许条件应单独表示：

$
Allowed_k(s,p),\qquad
P_k^{allowed}(s)=\{p\in P_k\mid Allowed_k(s,p)\}
$

例如 Open() 在锁定状态下仍然可以提交，但应被拒绝。

生成合法操作时可以从 Pₖᵃˡˡᵒʷᵉᵈ(s) 选择；测试拒绝行为时则需要从 Pₖ 中选择不满足 Allowed 的参数。
Allowed 不应默认等于契约适用范围 Dₖ，否则拒绝行为会落在规范之外。

### 4.3 候选来源不是另一份业务约束

枚举参数天然提供有限范围；String ID 等参数通常需要环境提供候选，例如当前订单 ID 列表。
测试层可以接收显式候选、上下界或环境查询结果，再调用同一份参数 Rule 筛选。

候选范围限制一次探索的范围，不必改变领域参数 Type。若只尝试三个订单，结论只能覆盖这三个订单及相应测试范围。
状态相关候选查询需要记录所使用的状态或观察版本，避免使用失效候选。
格式错误或基础 Type 之外的输入测试留给后续原始输入层，不要求第一版强类型 ActionInstance 覆盖所有畸形输入。

## 5. 状态转移及其契约

### 5.1 实际转移关系

固定 Action 类别 k，实现的行为关系为：

$
T_k^{impl}\subseteq S_0\times P_k\times O_k\times S_0
$

一次实际执行记为：

$
s\xrightarrow{k(p)/o}s'
$

参数已包含在 ActionInstance 中，因此也可记为 s —a/o→ s′。
确定性实现可表示为函数 fₖ(s,p) = (o,s′)；关系形式还允许同一输入产生多个结果。
没有产生输出不能自动解释成业务拒绝，超时、崩溃与不可观察必须单独处理。

### 5.2 契约而非执行代码

契约 Cₖ(s,p,o,s′) 定义哪些完成的转移符合要求。它不负责更新状态，不调用真实操作来生成自身的判断对象。

在约定范围内，符合性要求为：

$
D_k(s,p)\land T_k^{impl}(s,p,o,s')
\Rightarrow C_k(s,p,o,s')
$

该性质约束完成的转移；它本身不保证实现终止或在有限时间内响应。

一组带蕴含的 Rule 可以定义契约：

$
C_k(s,p,o,s')=\bigwedge_i
\left(P_i(s,p)\Rightarrow Q_i(s,p,o,s')\right)
$

Rule 的形参显式承担前状态、操作参数、输出和后状态四种角色。不能依靠变量恰好叫 before 或 after 来猜测角色，角色绑定应由测试层的声明或接口明确给出。

### 5.3 `implies` 的语法和语义（第一版已实现）

关键字确定为 `implies`，不保留 `imply`、`=>` 或 `==>` 作为别名。
它是中缀逻辑连接词：`P implies Q` 读作“命题 P 蕴含命题 Q”，不是执行命令。

合法语法与推荐格式分开规定：

- 前件可以是 Bool 或 RuleInstance 表达式，也可具有两者的联合 Type；包围前件的 `()` 可选。实例前件的含义是其规则检查成立，不是全局 Bool 隐式转换。
- 后件是单个 Bool 表达式时，包围后件的 `{}` 可选；多个 Bool 表达式必须使用 `{}`，块内条件按逻辑“且”组合。
- 推荐格式：仅当前件是单个 Bool 或 RuleInstance 变量引用时省略 `()`；其他前件使用 `()`。仅当后件是单个 Bool 变量引用时省略 `{}`；其他后件使用块。
- 格式化器按上述推荐格式输出，但解析器仍接受未使用推荐包围符的合法 Bool 表达式。
- `implies` 的优先级低于比较、`and`、`or`。例如 `a and b implies c == d` 解释为 `(a and b) implies (c == d)`。
- 第一版不支持链式蕴含或将蕴含当作可嵌入任意表达式的 Bool 运算符；它只作为 Rule 项使用。
- 无块的后件按现有表达式与语句边界解析，不将下一条 Rule 项隐式收进后件。复杂多行后件推荐使用块。

以下形式都合法：

```text
a implies b
(a and b) implies c
a and b implies c == d
a implies {
    b
    c == d
}
```

其中 `a and b implies c == d` 的推荐格式是：

```text
(a and b) implies {
    c == d
}
```

完整转移示例：

```text
let OpenTransition = rule (
        before: State,
        output: Decision,
        after: State,
) {
    '解锁时允许开门':
        (before['lock'] == '解锁') implies {
            output == '成功'
            after['door'] == '打开'
            after['lock'] == before['lock']
        }

    '锁定时拒绝开门':
        (before['lock'] == '锁定') implies {
            output == '拒绝'
            after == before
        }
}
```

这里 Decision 是包含“成功”和“拒绝”的输出枚举；Open 是无参数操作，示例省略单位参数。Runner 如何绑定这种签名仍需确定。`after == before` 的结构相等语义也需要验证或实现，不能仅以对象身份相同替代。

求值语义：

- `P implies { Q₁; …; Qₙ }` 表示 P ⇒ (Q₁ ∧ … ∧ Qₙ)；单表达式形式 `P implies Q` 是只有一个后件的情形。两者都不是赋值、状态更新或命令执行。
- 前提为假时，逻辑结论为真，但记录为“未触发”；后件不求值，避免无效分支中的字段访问或调用报错。
- 前提或已触发后件求值出错时，报告执行诊断，不能当成前提为假。
- 多条蕴含全部组合，按声明式合取理解，不采用首条匹配语义。
- 同一前提下允许多个结果应使用后件析取 P ⇒ (Q₁ ∨ Q₂)，不是两条分别要求 Q₁、Q₂ 的蕴含。
- RuleIR 需要保留前提、后件和源码来源，不能仅展开为普通 `or` 后丢失触发信息。

第一版将蕴含保留为独立 `Implication` IR 项；默认 checker 通过 `implications` 记录 `triggered`、`passed` 和 `consequents_checked`。实现复用现有条件跳转和条件记录指令，不新增 VM 指令。后件块内 `require`、嵌套和空块在第一版均拒绝；未来是否扩展另行设计。触发记录不等于已经实现分支覆盖分析。

### 5.4 覆盖、冲突与保持不变

实例前件现已支持：`Allowed(s, p) implies Q` 表示 $Holds(Allowed(s,p)) \\Rightarrow Q$。前件实例只构造并检查一次；不成立只令本蕴含未触发，不将前件违规升级成外层违规，检查出错则仍报错。此语义限于蕴含前件；否定及多个分支共享一次检查尚未扩展。RuleIR 保留原始实例 Term 与 Type，而不是不透明的 checker 调用；动态实例前件使用 TPIR3，兼容读取旧版 Bool 蕴含。

局部性质只要求条件触发时成立，不要求覆盖所有输入。完整行为契约则需要另行声明分支覆盖，例如：

$
D_k(s,p)\Rightarrow\bigvee_i P_i(s,p)
$

覆盖分支应显式标识，不能把所有通用辅助蕴含都算作行为分支。未命中分支时，报告“未覆盖”；是否让测试失败由契约的覆盖要求决定。

重叠分支默认同时生效。若同时生效的后件没有任何共同可满足结果，则契约冲突。仅证明前提覆盖还不够，也需要考虑后件是否可满足：

$
\forall(s,p)\in D_k,\quad\exists(o,s'):\ C_k(s,p,o,s')
$

有限、受支持的表达式子集可以做覆盖和可满足性分析；否则结果可以是 Unsupported 或 Unknown，不宣称已经证明。

未提到的字段不会自动保持不变。必须显式写相等约束，或未来提供语义明确的 frame/unchanged 简写。拒绝操作可以不改变业务状态，但仍允许在建模范围外写日志；需要由状态选择和 frame 规则明确边界。

## 6. 一个完整的小型测试模型

继续使用门禁例子：S 有三个合法状态，I 只有“锁定且关闭”。

两类 Action：

- Unlock：参数有“有效凭据”和“无效凭据”两种。
- Open：无操作参数。

Unlock 的转移契约草案：

```text
let UnlockTransition = rule (
        before: State,
        parameters: UnlockParameters,
        output: Decision,
        after: State,
) {
    '有效凭据可以解锁':
        (parameters['credential'] == '有效凭据') implies {
            output == '成功'
            after['lock'] == '解锁'
            after['door'] == before['door']
        }

    '无效凭据不得改变状态':
        (parameters['credential'] == '无效凭据') implies {
            output == '拒绝'
            after == before
        }
}
```

本例契约适用于所有合法状态和可构造参数。完整一步检查还要求后状态满足 StateSpace。

模型绑定的语义轮廓如下；这是配置结构说明，不是已经确定的 Tapas 语法：

```text
测试模型
    state: State
    state_space: StateSpace
    initial: InitialState

    operation Unlock
        parameters: UnlockParameters
        parameter_space: UnlockParameterSpace
        output: Decision
        transition: UnlockTransition

    operation Open
        parameters: 单位类型
        output: Decision
        transition: OpenTransition
```

被测实现另行绑定到 Unlock 和 Open，不嵌入上述规范中。
默认不得在调用实现前用 Allowed 替实现拒绝请求；允许将“仅探索合法操作”作为输入策略，而不是所有测试共有的执行语义。

示例轨迹：

```text
锁定/关闭
    -- Unlock(有效凭据) / 成功 --> 解锁/关闭
    -- Open() / 成功 ----------> 解锁/打开

锁定/关闭
    -- Open() / 拒绝 ----------> 锁定/关闭
```

第二条是通过的拒绝测试，不是失败测试。若实现返回“成功”并把状态变成“锁定/打开”，则同时违反 OpenTransition 和 StateSpace。

基础一步状态与调用组合共有 3 × (2 + 1) = 9 个。这个数量描述合法状态与可构造调用的组合，不自动表示它们都能在真实实现上直接初始化或从 I 到达，也不表示只测试一次就穷尽非确定性结果。

## 7. Runner、Evaluator 与 Trace

### 7.1 最小运行流程

1. 根据初始状态 Rule 和候选来源选择起点，建立或恢复被测环境。
2. 观察前状态，检查基础 Type、初始条件及相关状态规则。
3. 选择第 k 类操作，从其参数范围构造 ActionInstance。
4. 检查参数构造约束及契约适用范围。范围外调用报告 OutOfScope，不视为自动通过。
5. 调用实现或适配器，取得实际输出和后状态；先记录原始观察，再做 Type 与规则检查。
6. 绑定转移 Rule 的角色参数，执行 checker，并检查后状态约束。
7. 保存转移记录和诊断，根据预算、失败策略与输入策略继续下一步。

Runner 组织生命周期与角色绑定；Evaluator 解释 RuleIR。初期默认使用 checker，不要求每个用例指定 evaluator。空间生成、分析等 evaluator 可以后续接入，但不得复制业务条件。

### 7.2 轨迹和重放

$
\tau=s_0\xrightarrow{a_0/o_0}s_1\xrightarrow{a_1/o_1}\cdots s_n
$

每步至少记录 Action 类别、参数、输出、前后状态或可关联快照、规则结论、触发分支和违规来源。
重放还需要模型与实现版本、初始恢复方式、环境身份、候选/随机种子以及相关外部事件。

仅保存随机种子不保证外部系统可重放；不能恢复环境或控制相关非确定性时，只能承诺诊断记录或尽力重放。前后状态不得共享可被实现原地修改的快照引用，否则无法可靠比较变化。

### 7.3 结果语义

至少分开记录：

- 执行状态：完成、超时、崩溃、适配错误、规则求值错误、不支持、预算未完成；
- 业务输出：例如成功或拒绝；
- 规范结论：满足、违反、未覆盖、范围外；
- 测试预期：用例额外要求的具体分支或结果；
- 证据：Trace、失败转移、违规条件和覆盖信息。

接口命名应与现有 Result 协议协调，不在本文中冻结枚举名称。正确拒绝可以令测试通过；业务成功仍可能违反后置规则；超时不是业务拒绝；预算耗尽未发现失败不等于不存在失败。

## 8. 外部系统、部分观察与探索

若真实内部状态为 q ∈ Q，而测试仅能取得 h(q)，则 h: Q → S₀ 是观察映射。相同观察可能对应不同内部状态和后续行为，因此观察空间不一定是充分的完整状态模型。

必须声明状态是完整模型状态还是部分观察。可以通过历史扩展观察，也可以只检查可观察性质；不得仅凭部分观察宣称验证了全部内部状态转移。

输入策略可以依赖可观察历史 H：π(H) → k(p)。起步支持手写序列和有限枚举即可，之后扩展随机、边界、规则驱动生成及搜索。

一次测试验证观察到的转移；反例搜索寻找：

$
\exists\text{从 }I\text{ 开始的实际执行步骤 }(s,k(p),o,s'):
D_k(s,p)\land\neg C_k(s,p,o,s')
$

状态违规也应作为独立失败目标，或纳入完整 Cₖ。轨迹性质还可以约束操作顺序、请求对应关系等。
缩减必须重放并保持初始有效性、参数构造约束、契约适用范围及目标失败。拒绝测试不要求缩减后的参数满足 Allowed；错误地加入这个条件会把反例消掉。

## 9. 映射到当前 Retail 示例

| 模型角色 | 当前对应 | 下一步缺口 |
|---|---|---|
| 基础状态 | `model/model.tap` 中的扁平 `State`、状态和初始 Rule | 单商品订单及可信上下文；固定目录不属于可变状态 |
| 参数空间 | `Exchange(parameters)` 与 `InstanceOf[model::Exchange]` | 参数签名从 Rule 推导，调用边界检查同一运行时规则身份；约束成立单独检查，通用角色登记仍未实现 |
| 状态相关允许条件 | `ExchangeAllowed(previous_state, action_parameters)` | 用于判定成功/拒绝分支，不用于阻止测试执行 |
| 实现 | `implementation.tap` 的正确与缺陷实现 | 仅使用模型的基础类型、不调用规则；仅支持本地、无外部副作用的行为 |
| 转移约束 | `ExchangeTransition(before, parameters, output, after)` | 成功/拒绝蕴含及共同 frame 字段检查，与状态不变量分离 |
| 一步结果检查 | `ExchangeResult(previous_state, action_parameters, exchange_output, next_state)` | 在已验证的前状态与参数上，由模型内部用 `require` 组合转移与后状态不变量；保留完整违规路径和各规则的触发记录 |
| 实现接口 | `Function[State, ExchangeParameters] -> ExchangeExecution` | 正常返回含 `output` 与 `after`；执行器将返回 Type 放宽为 `AnyType`，在调用后验证结构，以保留类型错误证据 |
| 单步执行 | `run_exchange.tap` | `run` 检查初始集合，`step` 接受合法状态以继续执行；直接用 `arguments` 读取绑定实参并保存记录，仍不是通用测试包 |
| 拒绝测试 | `rejected_exchange.tap` | 六类请求均实际执行，验证正确拒绝及状态保持 |
| 反例搜索 | `exchange_counterexample.tap` | 三个候选中搜索完整失败转移，尚无多步探索或自动缩减 |

后续扩展方向（其中状态与参数分离、转移契约已有示例实现）：

- 状态保存订单、商品目录、支付及可信认证/确认上下文；确认应关联具体请求，不能只是任意调用可自报的布尔值。
- Exchange 参数包含订单 ID、原规格 ID、目标规格 ID、支付方式 ID 等调用输入。
- ExchangeParameterSpace 描述结构与构造范围；ExchangeAllowed 描述当前状态下是否允许换货。
- ExchangeTransition 用蕴含组合成功和拒绝分支，显式约束差价、订单更新及未变化部分。
- 正例与拒绝例只选择起点、ActionInstance 和预期分支；Runner 承担执行与检查。

当前例子仅模拟可支付额度随差价变化，不完整建模真实扣款、退款、库存更新或外部故障，不能将这些未来状态效果描述成已实现行为。确认仅绑定单步操作的目标规格，完整请求及版本绑定仍需扩展。接入 τ³ 时需由 adapter 和固定版本的上游契约明确实际状态变化。

## 11. 实施顺序与待决问题

### 11.1 建议顺序

1. 用门禁这类小型有限模型固定语义：状态组合、参数构造、成功、拒绝、状态违规。
2. `implies` 的 checker、IR、触发记录、解析器、格式化器与编辑器支持已有第一版；继续设计分支覆盖表达和汇总分析。
3. 增加最小的 Action 参数绑定、转移契约绑定与单步 Runner；先接纯实现，不新增复杂系统执行语义。
4. 实现有限候选枚举与范围信息，形成可保存的失败转移和简单多步 Trace。
5. 用同一模型切换正确/缺陷实现，验证测试确实发现缺陷，再改造 Retail 展示入口。
6. 后续加入恢复 adapter、生成、缩减、求解器及更复杂轨迹性质。

这不是要求当前立刻实现，需求编号用于后续追踪。

### 11.2 尚未冻结的设计

- Rule 作为空间定义需要显式包装，还是由使用位置声明角色？不预设 `space` 关键字。
- Action 参数类采用类型构造、普通包对象还是新声明语句？`ActionInstance` 是暂定概念名。
- 第一版 `implies` 已拒绝后件块内的 `require`、空块和嵌套规则；未来是否支持及如何组合结果诊断？
- 单个 Rule 如何标注“行为分支”和“辅助性质”，从而实现有意义的覆盖统计？
- 转移签名固定为四参数，还是显式角色映射？无参数 Action 如何保持接口一致？
- 状态结构相等、frame 约束及原始非法观察的保存方式如何落地？
- 类型范围与测试候选范围如何提供，而不污染领域规则？
- 对于纯度、环境依赖和不可分析调用，各 evaluator 如何声明支持能力？

判断语法是否值得加入的标准：它是否消除了用户反复编写的测试编排，同时保持空间、规则、执行与证据之间的数学边界清晰。不能仅因为某个对象可以用普通 Rule 编码，就要求用户手动承担其全部测试生命周期。
