# Tapas 运行机制

简体中文 | [English](Mechanism_en.md) | [项目主页](../README.md)

本文说明 Tapas 如何把源码编译成字节码，以及虚拟机如何管理状态、调用函数和释放复合值。
语言规则以[语言规范](Syntax_zh.md)和[类型系统](TypeSystem_zh.md)为准；本文只描述当前实现。

## 从源码到字节码

Tapas 文件、Markdown 代码块、命令字符串和 REPL 输入使用同一条编译管线：

```text
source
  -> document and lossless tokens
  -> AST
  -> names, scopes, and control-flow facts
  -> Type inference and checking
  -> bytecode
```

前端首先保存不可变源码和行索引，再生成包含空白与注释的无损 Token，并将语法解析为 AST。
语义阶段随后建立词法作用域、声明和名称引用；控制流分析记录节点关系、所在函数、确定返回和确定初始化等事实；Type 分析在同一结果上完成推断与检查。
只有前端没有错误时，后端才会分配环境槽位和临时槽位，并生成字节码。

这条管线由命令行程序和语言服务器共同使用，因此两者不再分别维护语法或 Type 规则。
具体的源码目录与依赖边界见[编译器结构](../src/compile/README.md)。

编译结果保存在字节码包装器中，其中包含：

- 32 位指令列表；
- 整数、浮点数和字符串常量表；
- 每条指令对应的文件名和源码位置；
- 环境槽位、临时槽位和运行栈所需的最大容量。

编译器已经确定普通名称对应的槽位，因此虚拟机执行变量访问时不再按名称查找。
包装器既可以立即执行，也可以保存为`.tapc`文件后再加载；相关命令见[使用说明](Usage_zh.md#编译和运行字节码)。
`.tapc`中的源码映射使用共享字符串表，并将连续相同的位置保存为一条游程记录；加载时会恢复完整的逐指令位置，包括 64 位行列号以及可空的源码和文件字段。因此压缩不会改变运行时错误的位置和上下文。
自动执行源码时，每个编译单元都会映射到以进程工作目录为根的项目级`__tapas_build__`目录树中。缓存校验会沿`OP_IMPORT`保存的源码路径递归比较源码、命令行编译器和产物的修改时间，因此任一传递依赖或开发构建更新都会使其导入者失效。文件头直接使用 Tapas 发布版本作为兼容标识，不再维护独立的字节码版本。

## 运行时状态

库是程序的根环境。
调用 Tapas 函数时，虚拟机会在函数定义时保存的父环境下建立调用环境。
需要跨表达式保留的值位于环境槽位，当前表达式的中间结果位于运行栈，局部临时值位于单独的临时槽位，函数返回值则暂存在虚拟机的返回位置。

例如：

```tapas
var mechanism_total = 0
mechanism_total = 1 + 2
```

第一条语句创建`mechanism_total`的环境槽位，并将整数常量`0`写入该槽位。
第二条语句从常量表读取`1`和`2`，在运行栈上完成加法，再将结果移入原有槽位。
赋值完成后，这次计算占用的栈值随即清除。

## 指令执行与函数调用

虚拟机按程序计数器依次读取指令，在同一个解释循环中解码操作码和参数；跳转指令直接修改程序计数器。

每次 Tapas 函数调用都有独立的调用帧，其中保存程序计数器、返回位置、调用环境、临时槽位、运行栈和循环游标。
虚拟机在同一个解释循环中切换这些调用帧，不会为 Tapas 函数递归进入新的 C 解释函数。
函数返回后，帧中持有的值会被清除，但已经分配的存储空间会保留，以供相同调用深度上的后续调用复用。

普通调用的参数在进入函数时写入预留的参数槽位，只有动态参数列表需要在调用期间直接读取调用者的运行栈。
同一深度再次调用同一个函数时，虚拟机可以复用已经验证的帧布局；改为调用其他函数时，仍会检查父环境、参数数量和各存储区容量。

`return this (...)`形式的直接尾递归不增加调用深度。
虚拟机会先保留新参数，再清空并复用当前调用帧，从函数入口继续执行。

函数值可以引用其定义位置的父环境。
返回的闭包需要继续使用当前调用环境时，运行时会保留相应环境，使闭包不依赖随后复用的调用帧。
循环游标也属于各自的调用帧，因此递归进入同一条循环指令不会改变外层循环的位置。

## 指令缓存

字节码只记录操作，不记录某次执行时观察到的值类别，也不会在执行过程中改写。
虚拟机为每份正在执行的代码维护独立缓存，并按指令位置直接访问缓存项。

循环、索引和函数调用第一次执行时走通用路径；同一位置反复遇到相同值类别或相同函数后，缓存允许后续执行直接进入对应实现。
实际值仍会接受必要检查；同一位置出现不同情况时，虚拟机会保留原指令并回到通用分派。

索引缓存可以直接处理 List 和 String 的单整数索引，以及 RealArray 和 BoolArray 的双整数索引。
稠密数组路径直接计算元素位置，但仍保留负索引、边界和写入 Type 检查；切片或不同值类别会回到通用路径。

缓存不写入`.tapc`文件，也不属于调用帧。
列表循环的位置则保存在调用帧中，并通过缓存预先分配的槽位访问，因此不同虚拟机和递归调用不会共享循环状态。

## 函数签名与运行时边界

参数和返回 Type 属于编译期函数签名。编译器用它检查函数体、静态可知的调用以及模块接口；
创建函数时不会把这些标注复制到 `tfunc`，调用帧也不会依据源码标注执行隐式检查。
运行时函数只保留执行所需的代码位置、闭包环境、参数数量和调用状态。

原生函数描述符中的 Type 字符串同样服务于编译器。根函数和包函数注册时，签名进入库级编译声明表；
原生函数对象自身只保留回调和参数数量约束。这样扩展仍能参与静态检查，而函数值不会获得一套
可反射、可重新绑定的运行时 Type 标注。

动态边界若要验证值，应显式调用 `types::matches`。`InstanceOf[R]` 在标注中也只参与编译期分析；
需要运行时规则身份 Type 时，使用 `types::instance_of(R)` 显式创建。

Rule IR 是有意保留的例外：它的参数 Type 是 Rule 的描述性 schema，供反射、求解、采样和序列化使用，
而不是附着在普通对象上的标注。根函数 `parameters` 因此只接受 Rule、RuleInstance 和 RuleIR，
不再接受 Function。

## 复合值的生命周期

String、List、Dictionary、Function 和其他复合值以`tcompo_v`为共同基础，并通过引用计数管理生命周期。
环境槽位、集合元素、运行栈和返回值都可能持有复合值。

复制一个持有关系时，运行时增加引用计数；覆盖或清除相应位置时，运行时减少引用计数。
值从运行栈移入环境槽位或返回位置时，可以直接转移原有持有关系，不必先增加再减少引用计数。
Int、Float 和 Bool 不持有复合值，从运行栈弹出这些值时只需移动栈顶位置。

引用计数降到零后，复合值通过自己的 vtable 释放。
List、Pair 和 Dictionary 还会依次释放其中持有的元素；稠密数组的标量数据由数组自身管理。

列表切片会先确定最终长度，再一次分配结果空间并连续复制元素，不会通过逐项追加反复扩容。
短 String 的字符数据直接保存在`tstring`内部，超过内部容量后才分配独立缓冲区。

引用计数不能发现不可达的循环引用。
当前运行时没有额外的追踪式循环回收器，因此程序应避免建立不再使用的容器引用环。

## 字节码格式

Tapas 字节码是抽象虚拟机指令，不是真实 CPU 指令。
每条指令使用 32 位无符号整数表示，最低 6 位保存操作码，其余位按指令需要解释为一个、两个或三个参数。

指令大致分为以下几类：

- 栈、槽位和常量操作；
- 跳转、条件分支和循环；
- 函数建立、普通调用、静态调用、闭包调用和尾调用；
- Type 前向声明与定义；
- Rule 建立、Condition 和子规则 Requirement；
- 索引读取、索引写入和导入；
- 算术、比较、逻辑和矩阵运算。

普通二元运算的两个参数直接表示运行栈中的左、右操作数偏移，不再使用额外的`PUSHINFO 0`描述栈—栈模式。`PUSHINFO`仍用于函数建立所需的对象槽位、临时槽位、栈容量和参数数量元数据。

当二元表达式的左操作数是可紧凑寻址的临时、局部或闭包名称时，二元指令会在自身参数中直接保存名称槽位；`IDXR`同样可以直接寻址命名接收者。常用小整数由`PUSHI`直接保存在指令中，线性的`for`退出清理可以由一条`POPN`同时释放栈值和临时槽。超出紧凑范围的闭包深度、索引参数数量、整数或清理数量仍使用原有指令序列，VM保留相应的融合路径，因此回退不会缩小语言能力。

操作码会随实现演进，完整枚举以[`tins`](../include/tapas/basic_defs/tbasis.h)为准，位布局和包装器结构以[字节码接口](../include/tapas/basic_defs/tbycs.h)为准。
将容易变化的逐指令清单保留在源码中，可以避免实现增加指令后文档继续给出过期数量或遗漏新指令。

## 蕴含前件的检查

`implies` 使用 `OP_RULEIMPLY` 记录原始 Bool/RuleInstance 前件，检查实例的成立性并在栈上留下 Bool，再使用现有条件跳转跳过未触发的后件。普通 Condition 的 Bool 要求不变。

源码元数据区分原始前件与本次缓存的成立结论；默认 checker 不重复检查前件，前件的违规也不并入外层 violation。公共 IR 保留原始 Term 和 Type。新生成的字节码应由配套的新运行时执行，不要假定旧运行时理解该内部模式；动态 IR 的 TPIR3 与字节码格式是两件事。

## Rule 否定的执行

普通 Bool `not`继续复用条件跳转。Rule 自身表达式中的`not`使用追加的`OP_RULENOT`：保留原操作数，对 Bool 直接取反，对 RuleInstance 执行一次非致命检查并取反`passed`。这是编译时确定的词法规则，不取决于普通函数是否恰好被 checker 调用。

源码 checker 将否定操作数与结果记录在独立的本次检查缓冲区，嵌套检查保存并恢复该缓冲区。这样不会扰乱 Condition/Implication 的记录顺序，也不会在整理检查结果时重复执行子规则。源码元数据生成显式 Not Term 与其操作数；动态 evaluator 直接解释 Not 节点。包含 Not 的 RuleIR 使用 TPIR4，与 VM 字节码格式独立；新 opcode 需要配套运行时。

## Rule 逻辑组合与裸实例项目

Rule 内的`and`、`or`使用`OP_RULETRUTH`检查实际执行到的 Bool/RuleInstance 操作数，再复用条件跳转保证短路。它们记录左右操作数和最终 Bool，供源码 IR 反射读取；不会为了反射补执行已跳过的分支。动态 And/Or 节点使用相同的有序短路语义，采用 TPIR5。

源码裸项目使用`OP_RULEITEM`：Bool 记录为条件，实例保留为子规则要求。静态已知实例的 IR 是 Requirement；动态实例也保留违规路径。`require`的词法和语法以及旧的专用操作码均已删除；内部 Requirement 与动态构造接口仍然保留。

## 查看字节码

示例程序位于[`examples/test_bycodes.tap`](examples/test_bycodes.tap)。
从仓库根目录运行以下命令，可以先编译该文件，再显示生成的字节码：

```sh
build/bin/tapas -cr docs/examples/test_bycodes.tap
```

C 会话 API 提供相同操作：

```c
#include "tapas/tsession.h"

int main(void)
{
    tsession *session = tsession_new();
    const char *source = "docs/examples/test_bycodes.tap";

    tsession_compile_file(session, source, 1);
    tsession_show_bycodes(session, source);
    tsession_free(session);
    return 0;
}
```

这些函数的声明与嵌入方式详见[C 交互](Foreign_zh.md)。

在 Tapas 内部，`__binary__()`显示当前库的字节码；传入 Library 或 Function 时，只显示对应对象关联的字节码或指令范围。
该函数只用于检查实现，不属于稳定的程序输出接口。
