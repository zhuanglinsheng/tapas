# 基础热路径逐项审查

本次检查全部 **30 组三语言实现，共 90 份源码**。结论是：原表混合了显式解释器内核、任务完成速度、对象表示和语言执行语义。语义等价足以支持任务对比，却不足以把所有耗时差距归因于 VM 指令执行。

基础热路径以定位瓶颈为目标：保留要测的操作，在此约束内优化写法。任务型结果用于发现能力缺口，同机制对照用于缩小原因范围，同一 Tapas 源码的运行时 A/B 用于验证优化。三者不能互相替代，不能只看跨语言比值就认定某条 VM 指令慢。

修订后各案例仍有明确用途，但需要遵守下表的解释边界。任务型默认实现保留惯用优化写法；七组具有明显实现差异的案例同时测 Python 结构对照并保存在原始数据中，不用较慢的对照替代默认参考，也不将其混入几何平均。[最新三语言表](../README.md) 由同一批测量生成，[原始样本](comparison_results.json) 记录全部时间、校验和、源码及二进制哈希。

## 两处实质问题已修正

**dp_row 的前驱行原先不是合法 LCS 状态。** 对右串 DCBAABCDDCBAABCD，旧行在首次出现 C 的第 2 列是 0，却在后面的 C（第 10 列）从 2 增长到 3。如果左前缀含 C，第 2 列至少为 1；如果不含 C，后来遇到 C 不会使 LCS 增长。这不是仅仅“写法不同”，而是输入状态缺乏真实算法来源。

现在前驱行来自左前缀 **ABCDAB** 与右串的真实 LCS，三语言均使用 `[0,1,1,2,2,2,3,3,4,4,4,5,5,5,6,6,6]`。反复测试向此前缀追加 A/B/C/D 后的单行更新，仍固定前驱行，不交换行。因此它是**单行递推内核**，不代表完整滚动 DP 的行交换、长期数据分布或完整 LCS 性能。新的固定校验和为 **260659**。

Python 的 enumerate 迭代、Tapas 的字符串索引、Lua 的 string.byte 在 ASCII 输入上提供相同的比较值，执行成本不同。保留 enumerate 默认实现，并另测 Python 索引版本；这可以观察迭代方式的影响。单行时间还含循环、字符访问、List 读写及条件分支，不能直接称为“纯整数 DP 运算成本”。

**dict_counting 原先没有进行计数。** 旧代码等价于 `counts[key] = counts.get(key, key)`，命中时只把原值写回；它无法覆盖频率统计需要的读取、加一、写回路径。现三语言均执行 `counts[key] = get_or(counts, key, 0) + 1`。校验改为计时外计算 `sum(count * (key + 1))`，默认结果 **1023701648**，防止只检查键数而漏掉错误计数。

本例明确测**显式循环中的 Dictionary 累加内核**，包括读取输入键序列；逐次 read/add/write 是合同的一部分。它不声称是完成整个整数频数任务的最快程序。完整任务与原生批量统计能力由 string_count / substring_count 的默认参考另行体现。

## string_count 的实现差异如何解释

Tapas 是字符迭代加 Dictionary 更新，Lua 是 gmatch 迭代加 table 更新，Python 默认是 Counter。三者构建完整字符频数表，算法意义相同；Counter 的批量路径执行位置与另外两者不同。它回答“完成完整字符直方图任务需要多久”，因此适合暴露标准库批量能力的差距。

若要判断显式循环里的字符迭代、散列键查找、整数加一和写回，必须同时看 `--matched` 的 Python 循环。默认 Counter 比值不能直接证明 VM 的单次 Dictionary 更新慢同样倍数；结构对照也无法完全消除三种语言的字符串缓存、整数装箱和对象布局差异。

输入限定为 ASCII。Lua 的 gmatch(".") 在这里是逐字符匹配迭代，仍有模式迭代成本；它不是裸指针扫描。Python 使用 Counter 的一般直方图能力，不能把本例改写成只查询四个已知字符、忽略完整频数表的捷径。

## 验证方式和剩余边界

[verify_hotspots.py](../verify_hotspots.py) 用完整二维 LCS 表作独立参考，验证 A/B/C/D 更新后的完整 17 元素行，检查 Python 两种写法和 Tapas/Lua。它还用 Counter 生成整数频数参考，在空输入、少量输入、全部键首次出现、部分键重复四种输入上核对键数、全部 4,096 个频数及加权校验和，此外使用包含 e/x/y/z 的字符输入核对 string_count 的完整频数表和两种 Python 实现；另以空输入、单元素、负数/重复值、有序、倒序及全相等输入核对 heap_callback 的完整出堆顺序和加权校验和，同时用重复优先级与不可排序 payload 检查三语言的完整记录保留、优先级顺序及加权校验和，共 12 项；新增 heap_order 的五类输入逐项检查两字段记录，共 15 项；再加 list_sort 五类输入的三语言完整排序输出 15 项，合计 **100 次**完整结果检查；不是只让两种实现互相对答案。[检查记录](kernel_checks.json) 含原源码哈希。

所有 46 项（三语言）仍由 [verify_semantics.py](../verify_semantics.py) 校验固定输入输出与综合算法小输入。报告运行器额外要求标记为需要诊断对照的 Python 案例与默认实现输出一致，并校验测量过程中源码未变。原始时间和结构对照来自同一批测量；四种分类不改变综合算法的 16 项范围。

`list_access`、`dict_lookup` 等 sink 只保留末次值，`list_update`/`dict_literal` 等只核对末态，这些常见微基准设计能减少额外归约工作，但不是完整运行时正确性测试。当前结论受其原语和输入形状限制，不能用几个样本覆盖所有键类型、别名、分配模式、miss 分布或缓存状态。

每次测量是独立进程；单独预热进程不能把 Python 自适应状态或 VM 缓存跨进程保留下来。大循环包含本轮建立缓存及优化的成本；Lua GC、Python/Tapas 引用管理、装箱及原生批量路径都属于实际任务成本。未通过硬件计数器进一步归因，不把语言间全部差异归结为解释器分派。

原始错误状态和伪计数源码保存在 [审查前快照](experiments/pre_hotspot_audit_sources.json)。两项语义修订后的时间不可与历史 A/B 当作同一输入直接合并。分类与简短测量说明来自 [catalog.json](catalog.json)，会自动进入两份 README；以后未登记的新案例显示“待审查”。


## 首次审查对性能定位的直接影响

以下数字记录引入 heap 包之前的审查批次，原始数据保存在
[审查批次样本](experiments/pre_heap_comparison_results.json)。后续重测结果以
上一级自动生成的 README 为准；[heap 实验](HEAP.md) 单独记录该包与算法写法的变化。

同批七次测量中，string_count 的 Tapas/Python 默认比值为 **1.707**，对 Python 显式循环为 **0.981**，后者差异很小，不能据此确认 Tapas 更快。它首先暴露的是原生批量直方图能力缺口。dp_row 默认比值 **1.257**，对索引结构对照仍为 **1.179**，说明迭代方式只能解释部分差距，组合内核仍值得分析。

tree_build 默认比值 **1.131**，对 Python List 树为 **0.615**，对象表示及叶子分配差异显著。while_search 默认 **1.890**、显式 while 对照 **0.877**，同样提示应区分原生扫描能力和解释器循环。这里只说明本次输入与构建下的结果，不把两种程序的时间相减当作单独某条指令的成本。

原表中范围物化、浅复制等很快，不能证明综合算法里指令组合也足够快：有些序列操作已进入原生实现，Python 的范围物化还包含本语言的整数生成/装箱成本；Counter、list.index 等方向则是 Python 原生能力占优势。现有 28 项仍缺少随机/聚集键、查询 miss、复合值覆盖、成功约束探测、变化的回调和对象形状等覆盖，不能据此声称已经囊括综合算法的全部真实热点。
