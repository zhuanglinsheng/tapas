# sieve 剩余差距诊断

本页记录紧凑序列优化前的诊断快照；紧凑容器、视图和循环优化的实现及最新结果见[本轮逐项优化](COMPACT_AND_SORT.md)。

当前 [sieve.tap](../sieve.tap) 使用 List、fill(List, Bool, Iterator)、count(List, Bool)；[sieve.py](../sieve.py) 使用 bytearray、步长切片赋值、bytearray.count。两者均为埃氏筛，输入 20000、结果 2262。Python 源码没有使用 tuple。

当时主表（源码归档见 [旧 sieve 源码](experiments/pre_compact_sieve_sources.json)）的七次单调用中位数为 Tapas 91 µs、Python 48 µs，耗时比约 1.90。此前 fill/count 已消除主要的逐元素 VM 循环，不能继续用修改前的逐元素循环解释当前差距。

## 当前实现的剩余成本

- Tapas List 每个槽位保存完整 16 字节 tobj；Python bytearray 每项一个字节。20001 个标记的元素区约为 320016 字节与 20001 字节。这是存储大小比例，不是耗时比例。
- fill 的 List+Iterator 路径已经在 C 中直接写槽位，标量路径没有逐元素引用计数。但每次迭代仍检查符号、负索引、边界和步长溢出，并写完整 tobj。当前输入调用 fill 34 次，共标记 35485 次。
- count 的 Bool 路径已避免通用对象比较，但仍逐个读取槽位类型和值；bytearray.count 对连续单字节数据计数。
- 初始化已使用倍增 memcpy，没有逐元素 VM append；但初始化的数据量仍大得多。
- 外层候选检查、算术、调用、34 个 Iterator 的创建和释放仍有 VM/对象成本。Python 使用 range 和一次 isqrt；Tapas 使用 while 及重复乘法。现有诊断没有单独量化这些子项，不能断言其占比或认定它们是最大瓶颈。

## 分阶段诊断

同一当前 Release 二进制，对初始化、标记（含外层循环）、计数分别加入 CPU 计时。每进程执行 300 次，先预热一个进程，再取三个进程的每次平均耗时中位数。

| 阶段 | Tapas List | Python bytearray | Python List 对照 |
| --- | ---: | ---: | ---: |
| 初始化 | 5.42 µs | 0.88 µs | 2.72 µs |
| 标记及外层循环 | 40.20 µs | 26.45 µs | 78.24 µs |
| 计数 | 9.22 µs | 3.53 µs | 182.58 µs |

[完整源码、样本及二进制摘要](experiments/sieve_current_phases.json)。Python List 对照保留相同筛法，替换成 Bool 列表、列表切片赋值和 list.count；它说明紧凑容器及对应批量操作很重要，但同时改变了容器操作实现，不能据此把全部收益精确归因于内存布局。

阶段计时增加了探针，重复调用改变了预热、分配和缓存状态，且不含函数返回与局部对象销毁，因此不能加总后替代主表单调用结果，也不能直接把两个实验的时间差当成某一成本的测量。

## 改善方向（设计建议，尚未实施）

1. 优先完善紧凑容器与通用批量操作的衔接。当前 BoolArray 已有一字节存储，但要求二维索引且没有 Iterable 能力；不能直接把 sieve 的 List 换成 BoolArray。可以设计显式一维可变视图，确定索引、遍历、生命周期和别名语义，再为 fill/count 提供直接底层实现。避免对 Pair/List 字典键隐式拆包，也不要偷偷改变二维数组的索引规则。
2. 优化现有 List+Iterator fill：识别可以证明全程有效的范围，选择无需逐次边界/溢出检查的循环；异常范围保留原来的顺序写入和部分成功语义。count 的标量扫描另测编译器向量化效果。这些属于低风险增量优化，但仍不能消除通用槽位的存储开销。
3. 最后根据隔离 A/B 判断 VM 外层循环和 Iterator 分配是否值得优化。切片语法可改善表达，但单独增加语法不会带来紧凑存储，也不会自动解决上述底层成本。

所有建议都应分别进行同语义 A/B，覆盖不同规模、步长、空范围、负索引、错误范围与别名；不通过添加筛法专用函数取得结果。
