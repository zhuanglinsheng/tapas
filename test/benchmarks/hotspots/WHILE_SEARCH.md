# 线性搜索热点诊断

主表 `while_search` 测量首个匹配位置的线性搜索任务。Python 默认使用原生 `list.index`，另保留 `--matched` 显式 while 控制；Tapas 和 Lua 都逐项循环。因此主表不能直接解释为 Python 的 while 更快。

## 当前同批次复测

3 轮，每轮各版本预热一次、正式测量 7 次；每次使用新进程，按固定种子打乱执行顺序，所有校验和均为 2750000。

| 实现 | 中位耗时 | Tapas/该实现 |
| --- | ---: | ---: |
| Tapas 显式 while | 52.566 ms | 1.000 |
| Python 3.14 显式 while | 58.917 ms | 0.892 |
| Python 3.14 list.index | 27.690 ms | 1.898 |
| Lua 显式 while | 27.785 ms | 1.892 |

[原始样本、版本、源码哈希和测量命令](experiments/while_search_diagnosis.json)。正式 benchmark 源码未修改。

## 两类缺口

Python 的原生接口把扫描放在 C 层。Tapas 每次搜索仍逐项解释执行 List 读取、边界判断、相等比较、条件跳转和索引递增。目标均匀变化于 0–7，匹配位置为 24–31，100,000 次搜索共执行 2,850,000 次元素比较。不能用返回 Bool 的成员检查或只返回数量的 count 替代首匹配位置，也不能预建字典来维持本例的线性搜索合同。

同结构 Python 对照中 Tapas 更快，说明不能将接近两倍的主表差距都归因于 while 调度。但 Lua 的同结构循环仍快近一倍，说明 Tapas 的扫描组合路径也值得优化。

当前 VM 已有标量比较/分支、算术/赋值等融合，但 List 下标读取后，`values[j] == target` 仍未形成完整的读取、比较、分支融合。现有索引比较消费器针对内部字符串字节，不能据此认为整数 List 扫描已获得相同融合。源码路径解释了可优化环节，尚未通过消融准确分摊 Lua 差距。

最近字符混合比较与动态初始化的运行时 A/B 对此例为 0.999，基本持平。这里没有字符串比较，内层也没有反复声明局部变量；固定局部槽位并非这个内核的首要目标。

后续分开处理通用首匹配位置的原生搜索接口，以及 List 读取、相等比较、条件分支的通用融合。优化须保持搜索顺序、自定义相等操作和边界语义，不能直接交换任意对象的相等操作数来套用现有快路径。
