# 六项综合算法的剩余差距

本文保留对应版本的实验快照；后续源码改进见 [惯用写法优化](IDIOMATIC.md)，当前结果以上一级最新 README 为准。

分析基于 2026-10-17 的普通 Release 主表：同一最终二进制、CPython 3.14.2、每项七次有效测量。下列诊断没有修改运行时或正式 benchmark 源码，也没有替换主表数字。优化一旦正式保留，应以最终构建重新运行 compare_script.py，同时更新两份 README、原始样本及校验记录。

## 当前差距与主要证据

| 案例 | Tapas/Python | 主要差异 | 是否主要缺 Python 语法 |
|---|---:|---|---|
| Dijkstra | 2.072 | Tapas 堆对记录执行 VM 比较回调；Python _heapq 使用 tuple 内建比较。还有记录表示、返回复制、sum 等差异，未逐项量化 | 否；tuple 表示和原生比较执行层次更关键 |
| Huffman | 1.822 | 当前 Tapas 逐字符更新频数字典，Python Counter 使用原生 _count_elements；但两侧对固定小字母表都有更快的 count 写法候选 | 否；当前源码没有充分使用已有原生计数能力 |
| sieve | 1.667 | Tapas 通用 List[Bool] 与 Python bytearray；fill/count 已消除内层 VM 循环，仍有存储密度、写入和扫描成本差异 | 切片赋值曾是接口差异；当前主要问题已不是没有这套语法 |
| longest_common_subsequence | 1.394 | Python 直接迭代字符/enumerate，Tapas 使用索引；索引、比较、分支及 DP 槽位读写的组合成本仍存在 | 迭代写法解释一部分，不能解释全部 |
| binary_trees | 1.311 | Python 使用紧凑不可变 tuple 并共享空 tuple 叶子；Tapas 每个叶子都是新的可变 List | 主要是对象表示及生命周期，tuple 的拼写不是加速原因 |
| sudoku | 1.211 | Python list.index 原生搜索首个空格，Tapas 用解释执行的扫描；for/else 还省掉显式 valid 状态 | 原生搜索贡献明显，for/else 只有较小影响 |

主表及同批结构对照见[中文报告](../README.md)、[英文报告](../README_en.md)与[原始样本](comparison_results.json)。下列单因素比值都是同一语言内的“变体/原版”，不是 Tapas/Python，也不是某一阶段的耗时占比。

## 本轮单因素诊断

每项三轮，每轮预热一次、七对独立进程交替执行并反转顺序，校验输出一致。保存完整变体源码、原始时间和二进制哈希：[remaining_gap_sources.json](experiments/remaining_gap_sources.json)。测量期间没有并行构建或测试。

| 单独变化 | 配对变体/原版 | 三轮 |
|---|---:|---|
| Python Huffman：Counter 改显式 dict.get 加一 | 1.687 | 1.726 / 1.654 / 1.620 |
| Python sieve：bytearray 改 Bool List，保留步进切片赋值和 count | 9.035 | 8.834 / 8.948 / 9.038 |
| Python LCS：内层 enumerate 改索引，外层仍直接迭代字符 | 1.085 | 1.084 / 1.086 / 1.085 |
| Tapas LCS：把左侧字符读取提至内层循环外 | 1.088 | 1.091 / 1.088 / 1.077 |
| Python binary_trees：tuple/共享空叶改为逐次新建 List | 1.259 | 1.261 / 1.259 / 1.257 |
| Python Sudoku：list.index 改显式 while，仍选同一个首个空格 | 1.153 | 1.148 / 1.153 / 1.157 |
| Python Sudoku：for/else 改显式 valid 标志，保留两个 range 循环 | 1.020 | 1.022 / 1.016 / 1.020 |

sieve 很短，每次进程内重复完整筛法 100 次并归一化 CPU 时间，以减少计时粒度影响。这也改变了进程内预热、分配器及缓存状态，不能用诊断的单调用时间替换正式主表的一次调用时间。9.035 说明的是两种 Python 存储及相应切片/count 实现的整体差异，不是纯内存带宽比例。

其余变体保留原 benchmark 重复次数。独立实验的比值不能相乘或相减，以声称已经精确拆出了各部分成本。

## Dijkstra：比较执行层次仍不同

优化后的严格字典序探针有 77,584 次比较，Python 相同顺序约 70,232 次；主要的比较次数差距已缩小，但每次比较的执行方式没有统一。Tapas 调用 distance_less 时仍需进入 VM、读取记录字段、比较、返回 Bool，再由 heap 检查结果；Python 默认记录的 tuple 比较在原生实现中完成。

新 heap_callback 任务包含相同输入的复制、建堆和有序出堆，同批 Tapas/Python 默认比值为 2.163；Python 改为 tuple 子类的语言级比较回调后，Tapas/该对照为 0.556。后一个控制还改变了 Python 对象表示，不能把差值当作精确回调开销，但它说明“比较在哪一层执行”比“两个语言是否都调用了 heap 包”更重要。

前期的统一并列顺序、Pair 替换、图查询探针以及公共帧入口试验分别见 [DIJKSTRA.md](DIJKSTRA.md) 与 [HEAP_OPTIMIZATION.md](HEAP_OPTIMIZATION.md)。不能把所有剩余时间都归因于比较回调：图遍历、记录读写、dist 复制和归约仍在计时内；当前没有逐阶段占比数据。

## Huffman：已有 count 可继续改善写法

正式源码统计 40,000 字符，而建树只有八个符号、38 次堆比较。Python Counter 的原生循环优势能解释当前差距的大部分形态：只把 Python 改成显式计数，完整案例从约 1.155 ms 增至 1.945 ms。不能因此把 1.822 倍差距解释为堆或递归速度。

进一步诊断发现，对于本来就固定为 abcdefgh 的小字母表，两侧可以对每个符号调用原生 count，并只保留正频数；Huffman 的节点构造、稳定初序及合并过程不变。

| 候选 | 原版中位数 | 候选中位数 | 配对候选/原版 |
|---|---:|---:|---:|
| Python Counter → 逐符号 str.count | 1.172 ms | 0.077 ms | 0.065 |
| Tapas 显式计数 → 逐符号 count(text, ch) | 2.062 ms | 0.077 ms | 0.037 |

完整源码和三轮样本见 [remaining_gap_huffman_counts.json](experiments/remaining_gap_huffman_counts.json)。七种小输入在原版/候选及两种语言上共 28 次检查，以独立最小权重合并的总代价验证。

这不是说当前正式主表已经变成 1.0，也不能将两次独立实验的中位数相除充当正式跨语言结果。它说明：本例有可以直接使用已有通用 API 的源码改善空间；保留时应同时选择各语言更好的写法、复核 Lua，并重新生成三语言报告。

逐符号扫描是 O(k*n)，原始直方图是 O(n)。小且已知的字母表适合这个方案，符号种类大时不应盲目替换。通用频数聚合是否仍有价值，应根据大字母表或一般 Iterable 的负载另行判断，而不是直接从这个八符号案例推出必须新增 Counter 包。

## sieve：批量接口补齐后，紧凑存储仍有优势

fill 和 count 已把合数标记与最终计数移到底层。当前 List 的每个 tobj 在本机占 16 字节，bytearray 的元素有效载荷是一字节：20,001 个标记对应约 320 KB 和 20 KB 的元素区。这个比较不包含容器头及临时对象，也不能直接推出耗时应相差 16 倍。

List fill 写入通用值槽位、处理索引与边界；Bool count 扫描类型和值。bytearray 的切片写入和 count 面向连续字节。即使两者都已在原生层执行，数据布局和每元素工作仍不同。Python 的步进切片是调用这些能力的语法入口；Tapas 用 fill 表达同样的标记任务，无须为这项性能专门复制切片赋值语法。

## LCS：迭代方式只解释部分，现有快路径还会影响源码选择

后续已补齐内部字节与普通 String 的比较路径，缓存字符不再承担此处描述的转换成本；LCS 也已恢复内层 `above` 声明。最新实现、回退分析及数据见 [值路径优化](VALUE_PATHS.md)。以下数值保留为改动前的诊断记录。

Python 内层改为索引后慢约 8.5%，但正式差距约 39%；当前 dp_row 对 Python 默认和索引控制分别为 1.351、1.259。两组证据都不支持“只添加 enumerate 就能消除差距”。后者仍是诊断内核，不能直接量化完整 LCS 的每条指令成本。

Tapas 字符提取外移反而慢约 8.8%，有明确的代码路径差异：[比较操作数发射](../../../src/compile/backend/ast_emit.c)会给直接参与比较的索引加提示，[vm_idxr_fast](../../../src/runtime/tvm.c)可以把这种单字节结果保持为内部立即值；两个索引结果直接比较时不必先成为一般 String 值。提取为局部变量后，一侧成为 String，混合比较会经过转换和字符串比较路径。单字节 String 本身已有规范对象缓存，不能误说每次都新分配一个字符对象。

这说明当前编译优化对表达式形状敏感；它是可推广到字符比较、循环不变量及值消费的编译器/运行时问题。并非要求用户故意重复索引，也不能以源码读取次数减少就断定更快。其余 DP List 读写、整数运算、分支及中间值成本仍需更细的剖析。

## binary_trees：逻辑节点数相同，新建对象数不同

本次任务遍历 3,407,872 个逻辑叶子及 3,375,108 个内部节点。Python 的 return () 复用同一个不可变空 tuple；内部节点仍逐个新建。Tapas 每次 return [] 都是新的可变 List，不能在语言层默认共享，否则会改变修改及别名语义。

当前 List 的小对象内嵌四个通用槽位：本机对象头 40 字节，加上四个 16 字节的 tobj，申请大小为 104 字节；实际分配器还可能按大小类别取整。已有池和内嵌存储减少了一部分成本，但没有消除额外叶子对象及引用生命周期。

Python 改用新 List 后约慢 25.9%，与主表约 31.1% 的差距处于相近量级，支持先关注表示及构造/释放成本。不能把独立批次数字相减当作剩余 VM 成本，也不能据此断言 Tapas 所有递归都慢；当前 Fibonacci 反而领先 Python。

## Sudoku：首个空格搜索比 for/else 更值得关注

Python list.index(0) 每次在原生层搜索首个空格；Tapas 是 VM while。仅把 Python 换成相同顺序的显式扫描，耗时增加约 15.3%。for/else 换显式 valid 状态仅增加约 2.0%，所以没必要优先给 Tapas 增加一套 for/else 语法。

其余候选检查包含索引算术、短路、条件退出、递归及回溯写入。现有 constraint_probe 是已填棋盘上的拒绝路径，Tapas/Python 为 0.879，不能用它证明完整数独的成功路径和回溯也领先。递归次数及循环/局部变量生命周期还应单独测，不能把剩余差距笼统归因于 List 索引较慢。

更有针对性的通用方向是原生线性查找、字符比较与 DP 的组合执行、紧凑对象/数据存储，以及减少必要的原生到 VM 比较调用。是否保留具体优化仍需同源码 A/B、退化原因分析和完整报告同步更新。
