# sort：原生排序优化与 A/B 验证

最新取样、分区及扩大矩阵的结果见[本轮逐项优化](COMPACT_AND_SORT.md)。以下保留首轮实现与实验记录。

本次优化保留 `sort(List) -> Nil`、原地不稳定排序和现有默认比较语义。数值精度、NaN 拒绝、字符串和递归 List 字典序规则不变。优化按值类型及输入顺序特征分派，不识别 benchmark 名称，也不修改固定 16 项综合算法。

## 实现

- Int、Float 和混合 Number 分别实例化同一私有排序模板，让同类型标量比较直接内联；混合数值继续使用精确比较规则。
- 数值采用三路 introsort，小分区使用插入排序；大分区采用九点取样，中止深度为 `2 floor(log2 n)`，耗尽后回退 heapsort。最坏时间为 O(n log n)，递归栈为 O(log n)。
- 完全有序、逆序、全等输入通过线性扫描处理。已有足够长升序前缀时尝试最多 n 次移动的插入排序，预算耗尽后继续常规排序。
- String、List 等比较较昂贵的值保留 libc qsort：小数组直接进入 qsort；大数组先做少量顺序取样，有序或局部有序时才尝试自适应路径。
- 标量合法性验证直接内联，复合值继续递归验证。完整移动 `tobj`，保持所有权、别名引用计数和 `compo_count`；比较错误延迟到临时持有的值已经放回数组之后报告。

实现：[sort.c](../../../src/stdlib/builtins/sort.c)、[sort_impl.h](../../../src/stdlib/builtins/sort_impl.h)。

## 原生 C 对照

环境为 macOS arm64、Release `-O3 -DNDEBUG`；构建配置和二进制 SHA 均记录在原始数据中。一个 C 进程中比较相同的 16 字节 `tobj` 数组，不经过 VM。两边均计入恢复输入的 memcpy；Tapas 一侧还包含合法性验证，libc qsort 一侧不包含。每轮预热一次，交替顺序，3 轮各 11 组配对。比较次数通过另一份不计时的模板实例统计。

下表为配对耗时比中位数（Tapas/qsort，越小越好）。

| 输入 | Int 512 | Int 8192 | Int 65536 | Float 512 | Float 8192 | Float 65536 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| random | 0.456 | 0.792 | 0.832 | 0.457 | 0.857 | 0.909 |
| sorted | 0.513 | 0.575 | 0.547 | 0.672 | 0.730 | 0.709 |
| reverse | 0.111 | 0.130 | 0.131 | 0.136 | 0.159 | 0.159 |
| equal | 0.556 | 0.619 | 0.600 | 0.674 | 0.723 | 0.705 |
| few_unique | 0.697 | 0.981 | 1.015 | 0.723 | 0.891 | 1.039 |
| nearly_sorted | 0.502 | 0.556 | 0.540 | 0.565 | 0.617 | 0.600 |
| organ_pipe | 0.667 | 0.807 | 0.846 | 0.723 | 0.837 | 0.867 |

42 组等权几何平均为 **0.547**，即耗时降低约 **45.3%**；40 组快于 qsort。随机输入耗时降低约 9%–54%。这只代表当前平台、值表示和测试矩阵，不表示所有 C 元素类型、平台和输入均优于 libc。

两组回退集中在 65536 个元素、8 种取值：Int 约慢 1.5%，Float 约慢 3.9%。不能直接把它们视为噪声：三路分区会增加这类输入的比较次数，例如 8192 个元素的对应诊断为 36968 对 26712 次。内联比较通常能抵消这部分成本，但昂贵比较无法保证，因此复合类型保留 qsort。另用相同完整内建函数契约复测 65536 元素重复值（3×11 组），结果如下，均仍比旧实现快约 2%。原生对照中的额外验证成本也必须计入解释。

| 类型 | 新/旧完整任务耗时比 | 配对比值 IQR |
| --- | ---: | --- |
| int | 0.979 | 0.972–0.993 |
| float | 0.978 | 0.965–0.989 |

## 低基数周期输入的进一步诊断

两项原生 C 回退都来自生成器 `key = i % 8`，不是随机分布的低基数数据。65536 元素时：

| 类型 | Tapas/qsort | 配对 IQR | 三轮配对中位数 |
| --- | ---: | --- | --- |
| Int | 1.015 | 1.002–1.030 | 1.011 / 1.015 / 1.020 |
| Float | 1.039 | 1.022–1.061 | 1.039 / 1.033 / 1.055 |

两者的比较次数均为 Tapas 295016、qsort 213080，前者多约 38.5%。三轮方向一致，尤其 Float 的配对 IQR 整体高于 1；仍需注意这不是独立样本置信区间。

源码还显示明确的取样与周期对齐问题：九点取样的步长 `n / 8 = 8192`，三组样点的键分别为 `[0,0,0]`、`[0,0,0]`、`[7,7,7]`，最终首个 pivot 必为最小值 0。第一次分区因此只消去 1/8 的相等项，其余 7/8 继续排序。这个取样弱点已能由源码和输入确定，但其对总耗时、总比较次数的独立贡献尚未做隔离 A/B，不能把所有退化都归因于它。

下一步应分别实验去相关取样、不良分区后的重新取样，以及减少移动的双端三路分区。验证扫描与排序内核也应分开计时。测试矩阵应补充打乱的低基数值、偏斜频率和不同周期/非整齐规模，避免只对 `i % 8` 修补。直接按键重建数组的计数排序不能无条件替代：必须保留完整值身份、混合数值表示、带符号零及别名。以上为后续建议，尚未修改当前排序实现。

## 完整任务 A/B

A 是优化前的同语义内建函数（含验证、同类型专用 qsort 比较器），B 是当前版本。输入构造在计时外，计时包含复制、排序和加权校验；每轮预热，交替执行。六类值、七种分布、8/512/8192 三种规模，共 126 组，每组 3×7 次配对。

| 类型 | 21 组新/旧耗时比几何平均 |
| --- | ---: |
| int | 0.887 |
| float | 0.903 |
| mixed | 0.864 |
| string | 0.916 |
| record | 0.932 |
| nested | 0.908 |

新增 `list_sort` 基础热路径使用 4096 个确定性随机整数，重复 16 次复制、标准排序和完整位置加权校验。其独立 3×11 次配对 A/B 比值为 **0.841**，IQR 为 0.810–0.859。Python 使用 `list.sort` 和 `sum(enumerate(...))` 生成式，Lua 使用 `table.sort` 和数字循环；这些参考写法也经过同语义 A/B 筛选。这里比较的是标准库排序任务，不要求不同语言采用同一种底层排序算法。

最新三语言结果已同步到[性能总表](../README.md)，固定综合算法仍保留指定算法。

## 退化分析与保留依据

| 尝试 | 发现与处理 |
| --- | --- |
| 简单三点取样 introsort | 近有序输入出现明显退化，嵌套记录最高约 4.71 倍；分区倾斜且破坏已有顺序。增加九点取样及受限插入排序。 |
| 所有输入先尝试插入排序 | 低基数输入产生额外 O(n) 次昂贵比较；仅在已观察到至少 n/8 的升序前缀时尝试。 |
| 复合值也完全改用三路分区 | 重复记录等仍慢约 10%–20%，比较次数增加能解释方向；普通复合输入保留 qsort，自适应路径处理有序输入。 |
| 复合值无条件预扫描 | 小数组重复准备工作一度造成约 25% 退化；小于 128 元素直接 qsort，大数组用少量取样跳过无收益扫描。 |
| Float 全等输入仍不够快 | 验证逐元素调用独立编译单元函数，线性快路径中占比突出；内联标量验证，单项诊断比值从约 1.017 降至 0.730，正式矩阵作为最终依据。 |

最终 126 组完整任务矩阵没有超过 5% 的退化项；小幅波动保留原始配对样本和轮次结果，不据单次数字断言收益。

## 正确性与复现

- 新增 1008 组 C 单元用例：6 类值、8 种分布、21 个边界规模；逐元素对照 qsort，并独立检查值身份多重集、共享引用计数和复合元素计数。覆盖整数极值、2^53 附近混合数值、无穷、带符号零。
- Release 全部 55 项测试通过，相关 ASAN 6 项通过。
- 46 组三语言 benchmark、14 组语义内核检查、94 组完整结果探针通过；benchmark 脚本 12 项单元测试通过。
- 正式原生/运行时 A/B、最新性能表及语义验证均使用相同 Tapas 二进制 SHA；主性能数据的 138 份源码摘要已逐一核对。

```sh
cmake --build build-release --target benchmark_sort
python3.14 test/benchmarks/native_sort_script.py build-release/benchmark_sort build-release/bin/tapas --json /tmp/sort-native.json
python3.14 test/benchmarks/sort_ab_script.py /tmp/tapas-before-native-sort build-release/bin/tapas --size 8 --size 512 --size 8192 --runs 7 --rounds 3 --json /tmp/sort-runtime.json
```
