# 堆比较回调诊断

当前主表已统一为三语言的显式优先级比较回调，见下文公平性修订。下面的诊断表保留修订前快照：当时 Python 默认使用原生 tuple 比较，不能与 Tapas 回调耗时直接比较。

## 历史同输入、同批次控制

输入为 256 条记录，重复 64 次复制、建堆与完全出堆。优先级由 `(i * 73 + 19) % 1009 - 500` 生成，256 个值互不相同，因而仅比较首项和默认字典序在本输入上给出相同顺序。不能将这个等价关系推广到有重复优先级的输入。

3 轮，各实现每轮预热一次、正式测量 7 次；固定种子打乱进程执行顺序，隔离字节码缓存，所有校验和均为 348023040。

| 实现 | 中位耗时 |
| --- | ---: |
| Tapas heap + 自定义首项比较 | 8.686 ms |
| Tapas heap + 默认 List 字典序 | 2.459 ms |
| Python heapq + 原生 tuple 比较 | 3.937 ms |
| Python heapq + Python __lt__ 比较首项 | 10.102 ms |
| Python heapq + Python __lt__ 转调 tuple.__lt__ | 15.624 ms |
| Lua 堆 + less 函数 | 8.097 ms |

Python 两个回调控制都使用 tuple 子类，包装在计时前完成。它们改变了对象表示，只用于当时的诊断，不能证明任意 Python 回调均比 Tapas 慢。原生 tuple 比较适合默认排序任务；显式回调机制测试则必须保留语言级比较。

Tapas 默认序控制使用与回调版完全相同的输入，不借用 heap_order 的数据；后者使用另一种包含大量重复优先级的分布，不能直接相减来计算回调成本。

[源码快照、版本、全部样本及独立工作计数](experiments/heap_callback_diagnosis.json)。该历史诊断未修改当时的正式源码。

## 成本位置

独立插桩计得完整任务有 155,520 次比较回调。插桩增加计数本身的执行时间，不作为性能证据。

每次回调通过 `tvm_services_invoke` 进入 VM，准备并切换函数帧，保留两个 List 参数，执行两次下标读取与一次比较，移交 Bool 并清理帧。heap 还检查比较结果类型以及堆长度/存储是否被回调改变。

函数帧已有池和相同函数复用路径，因此不能把这些操作都描述为每次 malloc。纯 Tapas 高阶调用热点也不能替代 C 扩展调用 Tapas 的入口：两者走的准备和所有权处理不同。

同输入默认序控制耗时约为回调版的 28%，说明回调相关路径是主要差异来源。但两者同时改变了函数入口、比较体、参数/结果管理和回调安全检查，差值不是纯函数入口成本。

最近字符比较和动态初始化优化对此例运行时 A/B 为 1.000，基本持平。本例比较的是整数记录，主要工作发生在原生堆反复调用短 Tapas 函数的组合路径。

## 优化方向与案例解释

若业务顺序能由默认字典序完整表达，应直接使用原生默认比较；本诊断仍保留显式比较函数来暴露回调成本。真正自定义顺序需要保留回调，例如只比较首项且允许并列、逆序或依赖其他状态。

运行时应优先优化可供所有 C 扩展复用的回调准备、参数与返回值管理，并优化短比较函数内部的下标/比较路径；不能识别本例函数名或把任意比较函数替换成首项比较。参数所有权、嵌套回调和错误清理仍需保持。

历史公共入口尝试已经发现重复增加快路径只带来约 3% 的局部收益，并引入其他负载退化，见 [通用堆优化](HEAP_OPTIMIZATION.md)。后续应减少真实工作，而不是复制已有帧池入口或删掉安全检查。


## 公平性修订（2026-10-18）

`heap_callback` 要回答的是“堆反复调用语言级比较函数时，完整任务的成本是多少”。若 Python 用原生 tuple 比较而 Tapas 用回调，即使唯一优先级输入得到相同结果，也没有测量同一种能力。现在三语言均执行自定义的优先级比较，payload 不参与比较，并列优先级的出堆次序不限。默认字典序任务仍由 `heap_order` 覆盖。

计时包含输入浅复制、建堆、完全出堆与加权归约；记录创建在计时前完成。Python 不强制逐行翻译 Tapas：采用 `__slots__` 记录对象及 `__lt__`，与 Tapas/Lua 的索引记录分别采用各自的惯用表示。

为避免有意选择较慢的 Python 参考，比较了三种相同优先级规则的写法：3 轮，每轮预热一次、测量 7 次，固定种子打乱顺序；三轮中位数再次取中位数：

| Python 回调表示 | 耗时 |
| --- | ---: |
| tuple 子类，读取两个首项 | 10.173 ms |
| list 子类，读取两个首项 | 10.127 ms |
| slotted record，读取两个 priority 属性（采用） | 8.229 ms |

这表示所检查候选中选择了更快的惯用写法，不是所有可能实现的最优性证明。[源码与全部样本](experiments/heap_callback_python_fairness.json)。旧表中“Tapas 快于 Python 回调”的局部结论不能推广到这个更快的 Python 表示。

独立计数显示，正式输入的完整任务中 Tapas 调用比较函数 **155,520** 次，Python **137,728** 次，Lua **139,520** 次。各语言允许采用合适的二叉堆调整策略；Tapas 的额外比较次数也属于实际堆实现成本。计数版不参与计时，[插桩源码和结果](experiments/heap_callback_fair_work_counts.json)。

因此主表结果能比较完整堆回调任务，但混合了堆策略、对象读取、比较函数、调用边界及安全检查；不能解释成同等次数、同等 ABI 的单次回调成本。若要定位运行时入口，必须在 Tapas 内部用同一源码和同一堆策略进行运行时 A/B。

除原有排序输出检查，还增加空输入、单元素、混合重复优先级和全相等优先级，payload 使用不可排序的字典。逐条检查优先级顺序、完整记录多重集和加权结果，允许任意合法平局次序。这样能发现误用默认字典序或只检查总和而遗漏记录的问题。三语言共增加 12 项检查，当前热点验证共 100 项；全部 46 项基准及 14 组综合算法内核也已通过。

修订后 Release 构建、Python 3.14、每项预热 1 次并正式测量 7 次，中位数如下：

| Tapas | Python | Lua | Tapas/Python |
| ---: | ---: | ---: | ---: |
| 8.623 ms | 8.344 ms | 8.046 ms | 1.033× |

本轮差距约 3.3%，不能凭这一小幅差距判断稳定退化；进一步判断需要重复批次和运行时 A/B。它也不能与历史 tuple 原生比较的约 2.2× 直接解释为性能改善。

当前完整测量见上一级 [中文报告](../README.md)、[English report](../README_en.md) 及 [7 次测量原始数据](comparison_results.json)。参考实现变化不代表 Tapas 运行时获得性能提升；旧结果保留于 [修订前快照](experiments/pre_callback_fairness_comparison_results.json)。
