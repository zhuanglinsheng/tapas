# 热路径优化实施与 A/B 分析

本次保留两项通用运行时修改：按操作码保留独立分派出口，以及有类型和缓存校验的 Dictionary 数值字段更新融合。运行时修改集中在 [tvm.c](../../../../src/runtime/tvm.c)，没有改写参与 A/B 的基准程序，也没有算法名称、字段名称、输入规模或校验和特判。最终数字见 [完整 A/B 表](dispatch_fields_original.md) 与 [原始样本](dispatch_fields_original.json)。

最终 3 轮、每项每版本 24 次有效样本：16 项综合算法耗时几何平均 B/A **0.971**（下降约 **2.9%**），27 项热点为 **0.941**（下降约 **5.9%**）。record_update 耗时下降 **33.4%**，LCS 和 Sudoku 分别下降约 **6.3%**，dp_row 和 recursive_loops 下降约 **3.5%**。

Dijkstra 的配对中位数为 1.014，调用基线为 1.022；这些小幅变化仍原样列出。调用基线三轮方向一致，不能简单断言没有真实代价；但也不能把小幅差异本身当作撤回整体改动的充分理由，需要结合 A/A 波动、生成代码及更多环境复验。

## 1. 修复分派结构，而不是只扩充局部快路径

原来的 `VM_NEXT()` 跳往共享的 `vm_advance`，大多数操作从同一个间接跳转点寻找下一条指令。简单热点只重复少数几种操作，综合算法却组合许多操作；一种局部融合让某个热点变快，并不能说明完整解释器的分派成本和生成代码也改善了。

现在各操作在自己的出口递增 PC、检查边界、读取下一条指令，再进行 computed goto。唯一的空汇编输入只阻止编译器把这些出口合并，不产生机器指令。原有 switch 备用分派仍保留。此类分派站点共享问题也见 [CPython 3.14 的说明](https://github.com/python/cpython/blob/3.14/Python/ceval_macros.h)。这解释优化方向，并不能代替本项目的测量。

第一次实现把每个融合分支都变成独立出口。进一步分析后，将同一操作码内部的分支汇合至 `vm_done_*`，再执行一次分派。这样保留操作码之间的预测上下文，同时减少同一操作码内部重复生成的分派代码。

本机 Apple Clang 21、arm64、Release + ThinLTO 的汇编证据如下，摘录及哈希见 [codegen.json](codegen.json)：

| 版本 | exec_tins 指令数 | 间接跳转站点 |
| --- | ---: | ---: |
| 原基线 | 20,186 | 3 |
| 允许编译器合并分派的对照 | 21,227 | 3 |
| 每个融合分支都有出口，含字段优化 | 26,074 | 93 |
| 最终按操作码汇合出口 | 25,324 | 60 |

去掉防合并屏障、其余分派语义相同的 [控制实验](dispatch_control.json) 显示，允许合并时又恢复到 3 个站点；保留独立站点对多个综合算法有改善。另一次只汇合同操作码出口的 [控制实验](per_opcode_control.json) 中，两个独立轮次均修复了此前的明显回退：相对逐分支出口版本，float_arithmetic 快约 9%，dict_delete 快约 12%–14%，function_call_baseline 快约 12%–13%。这些属于可以继续解决的代码生成问题，不能仅因第一次数据变慢就放弃。

这里也有成本：最终解释器函数仍比原基线大。未采集硬件分支失误或指令缓存事件，因此不能把全部性能变化精确归因于其中某个硬件事件，也不声称每一项都更快。

## 2. 字段更新融合：先解决额外成本，再保留收益

融合通用的九指令形状：两次常量字符串键的 Dictionary 字段读取、加减乘除、已有字段写回。它跳过中间栈值及相应指令分派，立即写回以保留别名和操作次序。

- 每次执行仍检查 Dictionary 接收者、数值类型、字段是否存在和缓存槽位。扩容、删除或替换对象之后，槽位必须重新校验。
- 缺字段、复合对象值、重载运算和父环境写入走原有路径。标量字段覆盖复合对象也退回原路径，保留引用释放行为。
- 推测性读取先检查槽位和父环境是否存在；整数除零也退回原指令执行，避免把错误提前到融合入口。预热缓存后的除零诊断与基线完全一致。
- 字节码形状只学习一次；动态类型失败不会把该形状永久禁用。普通字段读取学习“不匹配”，以后不反复读取和解释后继字节码。
- 形状状态与循环状态共用内联缓存中互斥的 union 成员，不增加本机每项缓存的大小。大段解析和校验代码在独立函数中，避免直接塞入主分派路径。

早期版本虽然让 record_update 快约 36%，却使部分浮点和调用热点明显退化。[早期样本](field_fusion.json) 和 [补丁](field_fusion.patch) 保留了这一结果。CPU 采样与字节码检查表明，浮点计时循环没有执行字段融合，回退发生在主解释器。旧版本汇编中，env 从常驻寄存器变为栈加载，说明新增代码影响了其他操作的生成代码。但这不是唯一解释：在 env 仍落栈的情况下，汇合同操作码出口也能修复明显回退，不能只凭一条额外加载就解释整个百分比。

因此后续依次隔离融合函数、缩小调用入口、学习字节码形状和不匹配结果，并修正分派复制粒度，而不是直接撤回字段优化。重构后的 [中间版本增量测试](field_incremental_v1.json) 用 3 轮交替顺序验证：相对只有独立分派的版本，record_update 的配对 B/A 为 0.828，三轮分别为 0.819、0.831、0.837。该表是中间版本的单因素证据，最终版本相对原基线的结果应看主 A/B 报告。

标量复制、扩大比较融合、原生调用后的连续算术、仅外提 Rule 分支等也做过探索，没有作为独立收益明确的运行时修改保留。最终没有改动 tval.c。早期 [组合样本](combined.json) 与 [组合补丁](combined.patch) 是历史实验，不能与最终二进制混用。

## 3. 小幅变化需要噪声对照

[A/A 对照](AA_RESULTS.md) 把同一个基线二进制同时作为 A 和 B，运行 3 轮，每项每轮 7 次，包含 Dijkstra、Sudoku、浮点、调用、字段更新等 10 项。多数轮次的中位数波动约为 1%–2%，浮点个别轮次约为 3.5%。这只是本轮环境的观察，不是固定的噪声上限。

因此不把一次 1%–2% 的变化自动称为退化或收益。最终 A/B 每项有 3 轮、每轮 8 次有效样本；每轮重新预热、轮换 A/B 先后顺序、打乱案例顺序。报告同时提供配对比值、四分位区间及各轮中位数。四分位区间不是置信区间；小效应若不能与 A/A 波动区分，应视为未确认变化。相反，跨轮次重复的 10% 以上变化不能一概解释为随机噪声。

## 4. 复现与验证

基线来自提交 `99ea72197b3e277c668a01124297b3ed7be1752e`，在修改运行时之前构建并保存为 `build-release/bin/tapas-ab-baseline`。来源及源文件 SHA-256 见 [基线记录](../ab_baseline.json)。两个版本使用同一编译器、Release `-O3 -DNDEBUG`、IPO 开启。JSON 保存二进制、构建参数、运行环境、每份基准源码的哈希和逐次样本。

```sh
cmake --build build-release -j4
python3 test/benchmarks/ab_script.py \
  build-release/bin/tapas-ab-baseline build-release/bin/tapas \
  --rounds 3 --runs 8 --seed 20261017
python3 test/benchmarks/compare_script.py build-release/bin/tapas --runs 7
```

A/B 对相同的 16 项综合算法、27 项热路径执行语义完全相同的程序。每次都是独立进程，使用程序内部 CPU 时间，排除启动和编译。全部校验和必须一致，运行器也检查源码和二进制在测量中没有变化。最终性能测量没有并行运行构建或测试；曾与兼容性测试重叠的一轮已终止并丢弃。

跨语言报告单独运行，不能把它和 A/B 的绝对时间相减；[中文 README](../../README.md) 与 [English README](../../README_en.md) 从同一次测量生成，包含全部 Lua 实现。

验证：Release **52/52** CTest 通过；AddressSanitizer 的 data_structures、core_no_stdlib、language_rules **3/3** 通过；A/B 及报告运行器测试 **8/8** 通过。回归覆盖预热后的别名、表扩容/删除、整数/浮点切换、数值与 Array 重载切换、复合目标释放、捕获变量、源码/字节码入口及异常定位。

备用 switch 模式的两个基础单测及新回归案例的源码/字节码入口通过。其完整 language_rules 在既有 recursive_frames 案例卡住，未优化基线也在 5 秒超时对照中同样复现；没有把这次未完成的检查算作通过，也没有把它算成本次性能修改的退化。

## 仍未解决的缺口

本次没有补齐 Counter、list.index 一类批量原生能力，也没有解决元组/紧凑节点表示差距。它改善的是一般 VM 分派和数值字段组合操作。Python 最佳惯用写法仍可能领先某些热点和综合算法；不能用平均值代替每个案例的结果。
